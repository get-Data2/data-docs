## R1. 측정 환경과 조건

- **Decision**
  - 전력 모드 25W(`nvpmodel -q` 결과 기록), **클럭 고정 안 함**(`jetson_clocks`는 sudo 필요)

    - 측정을 3번 나눠 하고, 묶음 사이 p95 차이를 기록한다
    - GPU·CPU 온도(`tegrastats`)를 측정 시작·끝에 기록한다. 80℃를 넘으면 식힌 뒤 다시 잰다
  - 측정 전에 다음을 확인한다
    - 우리 학습 프로세스(`python -m forecast run`, `anomaly train` 등)가 있으면 측정을 거부한다
    - 다른 계정의 GPU 사용: 10초 대기 동안 `tegrastats` GR3D_FREQ 평균이 정해진 값(기본 5%)을 넘으면 "경합"으로 표시하고, 최대 3회 다시 시도한다

  - 동적 클럭에서는 첫 실행들이 느리고 부하가 이어지면 클럭이 오른다. 워밍업과 반복으로 정상 상태를 잰다.
  - 같은 보드에서 t2 계정의 `forecast.py`가 GPU·메모리를 쓴다(2026-10-21 관찰). 통제할 수 없으므로 기록하고 다시 잰다.
- **Alternatives**: 클럭 고정을 관리자에게 요청할 수 있지만, 실제 운영도 동적 클럭이라 운영 조건에 맞는 측정이 된다. 필요하면 나중에 요청한다.

## R2. 추론 엔진 설치와 동작 확인

- **Decision**: pip 판을 `.venv`에 설치한다.
  - `onnxruntime-gpu` 1.31.0(CPU·CUDA EP 포함), `tensorrt-cu13` 11.4.0.106, `onnx`
  - 첫 작업(`edgeopt probe`)에서 작은 합성 모델(Linear·Conv1d·GRU)로 다음을 확인한다
    1. ONNX 내보내기
    2. ORT CPU·CUDA EP 실행과 결과 일치
    3. TensorRT 엔진 생성·실행과 결과 일치
    4. ORT TensorRT EP 사용 가능 여부
- **실패 시 대안 순서**
  1. TensorRT 공유 라이브러리 경로(`LD_LIBRARY_PATH`에 pip 패키지 lib)를 맞춘다. 대부분의 pip 휠 문제는 이것이다.
  2. ORT의 TensorRT EP로 엔진을 만든다(ORT가 자체 연결한 TensorRT 사용).
  3. `torch-tensorrt`(cu130 aarch64 휠이 있으면)
  4. 관리자에게 JetPack TensorRT(`nvidia-tensorrt`) 설치를 요청한다. 사용자 확인 항목이다.
  5. 그래도 안 되면 TensorRT 열은 "보드 미지원(사유)"으로 두고, 확인 기준 1번을 ONNX Runtime CUDA 기준으로 판정한다.
- **Rationale**
  - 시스템에 TensorRT가 없고 sudo도 없다. pip 휠은 SBSA(서버형 aarch64) 기준으로 빌드돼, Orin 통합 GPU(연산 규격 8.7)에서 동작이 보장되지 않는다.
  - PyTorch cu130이 8.7을 공식 목록에서 뺀 것과 같은 상황일 수 있다. 그래서 동작 확인을 먼저 한다.
- **Alternatives**: 처음부터 관리자에게 요청하는 방법이 있지만, 권한 없이 할 수 있는 길을 먼저 확인한다.

## R3. ONNX 내보내기

- **Decision**
  - 과제 3 모델은 `ForecastModel`을 그대로 내보낸다. 입력은 `past`(배치, 과거 칸, 특징), `future`(배치, 12, 특징), `space`(배치, 공간 수, 있을 때)이고, 출력은 (배치, 12, 2) 정규화 목표다.
    - 원 단위 복원(현재값 + 예측 × 표준편차)은 엔진 밖(FP32)에서 한다.
    - **반복 예측 모델이 최종이면** 12번 굴리는 반복이 그래프에 들어간다. 반복 안에서 쓰는 정규화 값(평균·표준편차·현재값)도 입력으로 내보낸다.
  - 과제 4 오토인코더: 공간마다 (배치, 12, 입력 열) → (배치, 12, 센서 열)
  - 연산 집합 버전 17, 배치 축은 동적(`dynamic_axes`), 시간 축은 고정
  - 내보낸 뒤 ORT CPU와 PyTorch CPU의 출력을 비교한다(1e-5 이내)
- **Rationale**
  - 시간 축을 고정하면 TensorRT가 최적화하기 쉽다. 서비스는 늘 같은 길이 창을 넣는다.
  - 엔진 안에서 FP16으로 원 단위까지 계산하면 CO₂ 수치(수백~수천)가 FP16 정밀도(상대 1e-3)로 바로 잘린다. 그래서 정규화 공간에서 끝내고 FP32로 복원한다(확인 기준 1ppm에 직결).
- **Alternatives**: TorchScript 경유는 TensorRT 연결이 약해 기각했다.

## R4. TensorRT 엔진 생성

- **Decision**
  - FP16 플래그를 켜고, 최적화 프로필은 배치 (최소 1, 최적 3, 최대 4)로 한다. 작업 공간 상한은 256MB이고 설정값이다.
  - 엔진 파일에 생성 환경(TensorRT·CUDA·드라이버 버전, GPU 이름)을 함께 기록한다. 버전이 다르면 서비스가 다시 만들도록 한다.
  - 정밀도 민감 층(마지막 Linear)을 FP32로 두는 옵션을 준비한다. 1ppm을 넘을 때만 쓴다.
- **Rationale**
  - README는 FP16을 요구한다. 엔진은 보드·버전에 묶여 이식되지 않는다.
  - 배치 3이 현재 운영 조건이고, 4는 공간 확장 가정이다.

## R5. 지연 측정 방법

- **Decision**
  - 입력: 과제 3 시험 표본에서 뽑은 고정 텐서(배치 1·3·4)를 장치 메모리에 미리 둔다. 전처리는 따로 1회 잰다.
  - 한 번 측정 = 호스트 입력 → (장치 복사) → 실행 → 장치 동기화 → 출력 호스트 복사. `time.perf_counter_ns`로 잰다.
    - GPU 방식은 `torch.cuda.synchronize()` / ORT 동기 실행 / TensorRT `execute_async_v3` + 스트림 동기화 뒤에 시간을 찍는다.
  - 통계: 평균·중앙값·p95·p99·최대, 3번 나눈 측정의 p95 범위
  - PyTorch CPU는 `torch.set_num_threads`를 기록한다(기본: 보드 코어 6). 스레드 수를 1로 둔 측정도 한다. 다른 모델과 공존할 때를 보기 위해서다.
- **Rationale**: GPU 실행은 비동기라 동기화하지 않으면 지연이 짧게 잡힌다. 서비스에서 실제로 기다리는 시간은 복사를 포함한 시간이다.

## R6. 전력·메모리 기록

- **Decision**
  - `tegrastats --interval 1000 --logfile`를 측정 동안 백그라운드로 돌리고, 끝나면 멈춘다.
  - 줄마다 시각, VDD_IN, VDD_CPU_GPU_CV, VDD_SOC(mW), GR3D_FREQ(%), RAM(MB), 온도(cpu·gpu·tj)를 읽어 측정 구간과 시각으로 맞춘다.
  - 지표
    - 대기 10초 평균 대비 측정 중 평균의 증가분(mW)
    - 1회당 에너지(mJ) = 증가분 × 측정 시간 / 반복 수
    - GPU 사용률 평균
    - 보드 RAM 증가분
  - 프로세스 메모리: `ru_maxrss`, GPU 할당(PyTorch `max_memory_allocated`, TensorRT는 엔진 장치 메모리 크기)
  - 측정 방식마다 **새 프로세스**에서 잰다. 앞 방식이 올린 라이브러리 메모리가 섞이지 않게 하기 위해서다.
- **Rationale**
  - 보드 RAM은 CPU·GPU 공유라 "GPU 메모리"가 따로 없다. 프로세스 RSS와 보드 RAM 증가분을 함께 본다.
  - 1초 간격 전력은 짧은 측정에서 거칠다. 반복을 늘려 측정 구간이 10초 이상이 되도록 한다.

## R7. 결과 차이(확인 기준 1)

- **Decision**
  - 과제 3 평가 시점 파일의 고유 (공간, t0) 표본 전체(약 4만 개)로 실행 방식마다 예측한다.
  - 기준은 PyTorch CPU FP32다. 실행 방식마다 다음을 낸다
    - CO₂ 원 단위 차이: 최대·평균·99%
    - 온도 차이(℃)
    - 시험 MAE 변화
  - 판정: CO₂ 최대 차이 ≤ 1ppm
  - 분류기는 같은 입력의 클래스 바뀐 비율(≤ 0.1%)이다.
  - 오토인코더는 점수 차이와, 과제 4 임계값 기준으로 경보 판정이 바뀐 칸 비율이다.
  - 넘는 표본은 시각·공간·입력 범위를 기록해 원인을 본다(예: 큰 표준편차를 곱하는 회의실 CO₂).
- **Rationale**
  - FP16 상대 오차 약 1e-3이다. 정규화 출력(대략 ±3)에 표준편차(CO₂ 약 250~430ppm)를 곱하면 최악 약 1ppm 근처다.
  - 그래서 최대값 기준 판정이 실제로 걸릴 수 있다. R4의 FP32 마지막 층 옵션을 준비해 두는 이유다.

## R8. 심화 1: INT8

- **Decision**
  - TensorRT INT8 보정(엔트로피 보정기)을 쓴다. 보정 표본은 **학습 기간** (공간, t0) 중 무작위 2,000개(씨앗 고정)다.
  - FP16 대비 지연·결과 차이·시험 MAE 변화를 비교한다.
  - 순환 신경망이 INT8을 지원하지 않으면 그 사실을 기록한다.
- **Rationale**
  - 보정 데이터에 시험 기간을 쓰면 시험 분포에 맞춘 셈이라 누수다(헌법 V).
  - 모델이 작아(파라미터 수만) INT8 이득은 작고 오차는 클 것으로 예상한다. 그것을 숫자로 보이는 것이 심화의 목적이다.

## R9. 심화 2: 동시 적재와 로컬 LLM 조합

- **Decision**
  - 서비스 구성대로 한 프로세스에 올리고, 총 RSS·보드 RAM 증가·배치 1 연속 실행 지연을 잰다.
    - 예측 1개, 오토인코더 3개, 분류기(과제 5), 공용 CUDA 컨텍스트
  - 실행 방식마다(PyTorch GPU / ORT / TensorRT) 잰다. CUDA 컨텍스트와 라이브러리 적재 크기가 방식마다 크게 다르다.
  - 로컬 LLM은 아직 정해지지 않았다. 크기 가정별 메모리를 추정한다.
    - 1B·3B·7B, 4비트 가중치 ≈ 파라미터 × 0.5바이트 + KV 캐시·런타임 여유
    - 보드 7.3GB에서 OS·수집기·서비스 몫을 뺀 남은 메모리와 비교해 가능한 조합 표를 낸다.
  - 실제 LLM이 정해지면 같은 명령으로 다시 잰다.
- **Rationale**: 과제 7 상황의 "임베딩 모델, 로컬 LLM이 같이 돈다"에 대한 직접 답이다. 메모리가 가장 먼저 부족한 자원이다(과제 3 학습 때 실측).
