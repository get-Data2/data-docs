# Feature Specification: 엣지 최적화 (과제 7)

**Feature Branch**: `007-edge-optimization`

**Created**: 2026-10-21

**Status**: Ready for plan

**Input**: User description: "과제 7 엣지 최적화 (README '과제 7' 전체 + 심화 B 2개). 학습한 모델(예측·이상 탐지·분류)을 TensorRT FP16으로 변환,
PyTorch CPU·PyTorch GPU·ONNX Runtime·TensorRT의 지연(평균·느린 쪽 5%)을 배치 1·4로 측정, 변환 전후 결과 차이를 원 단위로,
측정 중 전력·GPU·메모리 기록. 확인 기준: CO₂ 예측 차이 1ppm 이하, 분류 바뀐 비율 0.1% 이하, 측정 조건 기록.
심화: INT8 변환, 모델 4개 동시 적재 총 메모리와 로컬 LLM 조합 제안."

## 배경 (2026-10-21 보드 확인)

- **보드**
  - Jetson Orin Nano Engineering Reference Developer Kit Super, L4T R39.2.1, 전력 모드 **25W**(`nvpmodel -q`)
  - GPU Orin(연산 규격 8.7), 드라이버 595.78, CUDA 13.2
  - RAM 7.3GB를 CPU와 GPU가 **함께** 쓴다
- **권한 제약**: sudo가 없다.
  - `jetson_clocks`(클럭 고정)와 `nvpmodel` 변경을 할 수 없다. 측정 조건은 "25W, 클럭 고정 안 함"이다. 반복·워밍업·온도 기록으로 흔들림을 보완한다.
  - `tegrastats`는 sudo 없이 동작한다. 전력 레일 VDD_IN·VDD_CPU_GPU_CV·VDD_SOC(mW), GPU 사용률(GR3D_FREQ), RAM을 1초 간격으로 읽는다.
- **추론 엔진**
  - 시스템에 TensorRT·ONNX Runtime이 없다.
  - pip로 받을 수 있는 판: `tensorrt-cu13` 11.4.0.106(aarch64), `onnxruntime-gpu` 1.31.0, `onnxruntime` 1.31.0
  - **Orin(통합 GPU, 연산 규격 8.7)에서 실제로 동작하는지는 아직 검증하지 않았다.** 첫 작업이 동작 확인이다.
- **PyTorch**: `2.14.1+cu130`. Orin을 공식 지원 목록에서 빼지만, CPU와 수치가 일치함을 확인했다.
  - LSTM·GRU: 1e-6 수준
  - 합성곱: TF32를 끄면 일치
- **같은 보드의 다른 작업**: 다른 계정(t2)의 프로세스가 같은 GPU·메모리를 쓴다(2026-10-21 관찰). 측정 중 이를 `tegrastats`·`nvidia-smi`로 기록한다.
- **공간 수**: 우리 공간은 3개(실습실·사무실·회의실)다. README의 "네 공간 한꺼번에"는 배치 3(현재)과 배치 4(공간 확장 가정) 둘 다 잰다.

### 변환 대상 모델

| 모델 | 출처 | 입력·출력 | 비고 |
|---|---|---|---|
| 60분 예측(최종) | 과제 3 `var/forecast/bundle/` | 과거 창 × 특징 + 미래 12칸 정보 → 12 × 2(CO₂·온도) | GRU·LSTM·TCN 중 선택된 것 |
| 60분 예측(비교용 3종) | 과제 3 `var/forecast/runs/`(심화 1의 GRU·LSTM·TCN, 같은 과거 길이) | 같음 | 생각해 볼 점 Q2(순환 vs 합성곱) |
| 이상 탐지 오토인코더 | 과제 4 `var/anomaly/bundle/` | 1시간 창 × (센서 열 × 2 + 시간 5) → 창 × 센서 열 | 공간마다 열 수가 다르다(3개 모델) |
| 상태 분류기 | 과제 5 `var/state/bundle/` | 특징 벡터 → 클래스 확률 | 신경망이면 변환한다. 트리·선형 모델이면 변환하지 않고 CPU 측정만 한다(해석에 이유를 적는다) |

## 용어

| 용어 | 뜻 |
|---|---|
| 실행 방식 | PyTorch CPU, PyTorch GPU, ONNX Runtime(CPU·CUDA), TensorRT FP16(·심화 INT8) |
| 지연 | 입력 텐서가 준비된 뒤 출력이 호스트 메모리에 올 때까지의 시간(데이터 전처리 제외, 장치 복사 포함) |
| 느린 쪽 5%(p95) | 반복 측정한 지연의 95번째 백분위수 |
| 결과 차이 | 같은 입력에서 기준(PyTorch CPU FP32)과의 출력 차이를 **원래 단위**로 잰 값(CO₂ ppm, 온도 ℃, 분류는 바뀐 비율) |
| 측정 조건 | 전력 모드, 클럭 고정 여부, 워밍업 횟수, 반복 횟수, 배치, 온도, 같은 보드의 다른 GPU 사용 여부 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 모델을 보드 전용 엔진으로 바꾼다 (Priority: P1)

운영자는 학습한 모델들을 TensorRT FP16 엔진으로 바꿔, 과제 8 서비스가 쓸 수 있는 파일로 받고 싶다.

**Why this priority**: 해결할 것 1번. 이후 모든 측정과 과제 8의 전제다.

**Independent Test**: 명령 하나로 모델마다 중간 형식(ONNX)과 엔진 파일이 생기고, 입력 규약 버전·해시가 기록된다.

**Acceptance Scenarios**:

1. **Given** 과제 3 모델 묶음, **When** 변환하면, **Then** ONNX 파일과 TensorRT FP16 엔진이 생긴다. 배치 축은 1~4를 받는다.
2. **Given** 공간별 오토인코더 3개, **When** 변환하면, **Then** 공간마다 엔진이 생긴다.
3. **Given** 변환이 실패한 연산(예: 순환 신경망 일부 연산), **When** 변환하면, **Then** 실패 원인과 우회 방법(연산 집합 버전 변경, 고정 길이 등)이 기록되고 다른 모델 변환은 계속된다.
4. **Given** pip TensorRT가 이 보드에서 동작하지 않음, **When** 동작 확인을 하면, **Then** 원인과 대안(시스템 TensorRT 요청 등)이 기록되고 나머지 실행 방식(PyTorch·ONNX Runtime) 측정은 그대로 진행된다.

---

### User Story 2 - 실행 방식별 지연을 잰다 (Priority: P1)

분석가는 실행 방식 × 모델 × 배치(1·3·4)마다 지연 평균과 p95를 같은 조건으로 잰다.

**Why this priority**: 해결할 것 2번, 산출물 표의 핵심이다.

**Independent Test**: 측정 결과 표에 실행 방식 × 모델 × 배치마다 평균·p95·반복 수·워밍업 수가 빈칸 없이 있고, 지원하지 않는 조합은 이유가 적혀 있다.

**Acceptance Scenarios**:

1. **Given** 모델과 실행 방식, **When** 측정하면, **Then** 워밍업(기본 50회) 뒤 반복(기본 1,000회)한 지연의 평균·중앙값·p95·p99·최대가 나온다.
2. **Given** 측정, **When** 측정 조건을 보면, **Then** 전력 모드, 클럭 고정 안 함, GPU·CPU 온도(시작·끝), 다른 계정의 GPU 사용 여부가 함께 기록된다.
3. **Given** 같은 측정을 다시 하면, **When** 비교하면, **Then** p95 차이가 정해진 범위(기본 ±20%) 안이다. 벗어나면 측정 조건 차이를 기록한다.

---

### User Story 3 - 변환해도 결과가 같은지 잰다 (Priority: P1)

운영자는 변환 뒤에도 예측·탐지·분류 결과가 사실상 같은지 원래 단위로 확인하고 싶다.

**Why this priority**: 확인 기준 1번이다. "결과는 똑같이"가 이 과제의 조건이다.

**Independent Test**: 과제 3 시험 표본 전체에서 실행 방식마다 기준 대비 CO₂ 최대·평균 차이(ppm), 온도 차이(℃), 분류 바뀐 비율이 나오고 판정표가 자동으로 나온다.

**Acceptance Scenarios**:

1. **Given** 과제 3 평가 시점 파일의 시험 표본, **When** 실행 방식마다 예측하면, **Then** 기준(PyTorch CPU FP32) 대비 CO₂ 차이 최대·평균·99% 값(ppm)과 온도 차이(℃)가 나온다.
2. **Given** CO₂ 최대 차이, **When** 판정하면, **Then** **1ppm 이하**면 통과다. 넘으면 그 표본(시각·공간)과 원인을 기록한다.
3. **Given** 분류기, **When** 같은 입력으로 비교하면, **Then** 클래스가 바뀐 비율이 **0.1% 이하**면 통과다.
4. **Given** 오토인코더, **When** 비교하면, **Then** 이상 점수 차이와 그로 인한 경보 판정(임계값 넘음 여부)이 바뀐 비율이 나온다.
5. **Given** 시험 성적, **When** 보면, **Then** 엔진의 시험 MAE가 과제 3 원래 MAE와 얼마나 다른지도 나온다(차이가 오차보다 훨씬 작음을 보인다).

---

### User Story 4 - 자원 사용량을 기록한다 (Priority: P1)

운영자는 각 실행 방식이 전력·GPU·메모리를 얼마나 쓰는지 알고 싶다. 같은 보드에 다른 모델(임베딩, 로컬 LLM)이 함께 올라가기 때문이다.

**Why this priority**: 해결할 것 4번, 산출물 표의 열이다.

**Independent Test**: 측정마다 평균 전력(VDD_IN·VDD_CPU_GPU_CV, mW), GPU 사용률, 프로세스 메모리, 보드 RAM 증가분이 나온다.

**Acceptance Scenarios**:

1. **Given** 측정, **When** 진행되는 동안, **Then** `tegrastats` 기록(1초 간격)이 측정 구간과 시각으로 연결돼 저장된다.
2. **Given** 측정 전 대기 구간(기본 10초), **When** 비교하면, **Then** 측정 중 전력에서 대기 전력을 뺀 증가분과 추론 1회당 에너지(mJ)가 나온다.
3. **Given** 메모리, **When** 보면, **Then** 프로세스 최대 RSS와 GPU 할당(가능한 경우)이 나온다. CPU·GPU 메모리 공유 구조임을 해석에 적는다.

---

### User Story 5 - 최적화 보고서 (Priority: P2)

운영자는 실행 방식 × 모델별 지연·오차·메모리·전력 표와 결론("과제 8 서비스는 ○○로 돈다")을 받는다.

**Why this priority**: 산출물이다.

**Independent Test**: 보고서에 표·그래프·측정 조건·결론·생각해 볼 점 3개의 답이 있다.

**Acceptance Scenarios**:

1. **Given** 측정 결과, **When** 보고서를 만들면, **Then** 표에 지연(평균·p95, 배치 1·3·4), 결과 차이, 메모리, 전력, 에너지가 함께 나온다.
2. **Given** 결론, **When** 읽으면, **Then** 과제 8이 쓸 실행 방식과 엔진 파일, 그 이유가 있다.
3. **Given** 생각해 볼 점
   - Q1(CPU로 1ms면 충분한데 왜 변환하나)
   - Q2(순환 vs 합성곱 중 무엇이 더 빨라지나)
   - Q3(평균보다 p95가 중요한 이유)

   **When** 답하면, **Then** 측정 숫자를 근거로 든다.

---

### User Story 6 - 심화(B): INT8과 동시 적재 (Priority: P3)

1. **INT8**: TensorRT INT8로 변환한다.
   - 보정 데이터는 **학습 기간** 표본만 쓴다(시험 미사용).
   - FP16 대비 속도 이득과 정확도 손실(CO₂ ppm 차이, 시험 MAE 변화)을 비교한다.
2. **동시 적재**: 예측·오토인코더 3개·분류기를 한 프로세스(또는 서비스 구성대로)에 함께 올렸을 때 총 메모리를 잰다.
   - 로컬 LLM 크기 가정별로 함께 올릴 수 있는 조합을 제안한다.
   - 가정: 1B·3B·7B 파라미터, 4비트 양자화 기준 추정. 실제 LLM이 정해지면 다시 잰다.

---

### Edge Cases

- **pip TensorRT·ORT GPU가 Orin에서 동작하지 않음**: 동작 확인(US1-4)에서 실패하면 원인을 기록하고, 대안 순서(research R2)대로 시도한다. 끝내 안 되면 TensorRT 열은 "보드 미지원(사유)"으로 남기고 확인 기준 1번은 ONNX Runtime 기준으로 판정한다. 이 사실을 결론에 적는다.
- **순환 신경망 변환 실패·느림**: LSTM·GRU는 TensorRT에서 루프 연산으로 바뀌어 이득이 작거나 변환이 안 될 수 있다. 실패도 결과로 기록한다(Q2의 근거).
- **FP16 넘침**: 정규화된 입력이라 범위 문제는 작다. CO₂ 원 단위 복원은 엔진 밖(FP32)에서 한다.
- **측정 중 다른 프로세스의 GPU 사용**: 측정 전후 GPU 사용률이 대기보다 높으면 그 측정을 표시하고 다시 잰다(최대 3회).
- **열 조절(쓰로틀링)**: GPU 온도가 정해진 값(기본 80℃)을 넘으면 기록하고 식은 뒤 다시 잰다.
- **과제 5 분류기가 트리 모델**: TensorRT 변환 대상이 아니다. CPU 지연만 재고 "변환 불필요(이미 μs 단위)"로 적는다.
- **모델 묶음이 아직 없음**(과제 3·4·5 미완): 해당 모델 측정은 건너뛰고 표에 "대기"로 둔다. 나머지는 진행한다.

## Requirements *(mandatory)*

### Functional Requirements

**변환**

- **FR-001**: 모델 묶음(과제 3·4·5)을 읽어 ONNX로 내보낸다. 배치 축은 동적(1~4)이고, 시간 축은 모델 입력 규약의 고정 길이다.
- **FR-002**: ONNX에서 TensorRT FP16 엔진을 만든다. 엔진 파일, 만든 TensorRT 버전, 최적화 프로필(배치 1·3·4), 원본 모델 해시를 기록한다.
- **FR-003**: 변환이 실패하면 단계(내보내기 / 엔진 생성)와 오류를 기록하고 다른 모델을 계속 변환한다.
- **FR-004**: 첫 단계에서 pip TensorRT·ONNX Runtime GPU의 동작을 작은 합성 모델로 확인하고 결과(동작 / 실패 사유)를 기록한다.

**측정**

- **FR-010**: 실행 방식 4종(PyTorch CPU, PyTorch GPU, ONNX Runtime CPU·CUDA, TensorRT FP16) × 모델 × 배치(1·3·4)의 지연을 잰다.
  워밍업·반복 횟수는 설정값이다(기본 50·1,000). 평균·중앙값·p95·p99·최대를 낸다.
- **FR-011**: 지연은 장치 동기화 뒤 잰다(GPU 비동기 실행 때문). 입력은 미리 만든 텐서를 쓰고, 전처리는 지연에 넣지 않는다. 전처리 시간은 따로 한 번 잰다.
- **FR-012**: 측정마다 `tegrastats`(1초)를 함께 기록해 평균 전력, 대기 대비 증가분, 1회당 에너지, GPU 사용률, 온도를 낸다.
- **FR-013**: 측정마다 프로세스 최대 RSS와 GPU 할당(가능한 경우), 보드 RAM 사용량(측정 전·중)을 기록한다.
- **FR-014**: 측정 조건을 기록한다: 전력 모드(`nvpmodel -q`), 클럭 고정 안 함, 반복·워밍업, 배치, 온도, 다른 계정의 GPU 사용 여부, 소프트웨어 버전(torch·ORT·TensorRT·CUDA).

**결과 차이**

- **FR-020**: 과제 3 평가 시점 파일의 시험 표본 전체로 실행 방식마다 예측을 내고, 기준(PyTorch CPU FP32) 대비 원 단위 차이(CO₂ ppm, 온도 ℃: 최대·평균·99%)를 낸다.
- **FR-021**: 분류기는 같은 입력에서 바뀐 클래스 비율, 오토인코더는 점수 차이와 경보 판정이 바뀐 비율을 낸다.
- **FR-022**: 확인 기준 판정표를 자동으로 만든다: CO₂ 최대 차이 ≤ 1ppm, 분류 바뀐 비율 ≤ 0.1%, 측정 조건 기록 여부.

**산출물**

- **FR-030**: 최적화 보고서 `docs/deliverables/task7/`: 실행 방식 × 모델별 지연(평균·p95, 배치 1·3·4)·오차·메모리·전력 표, 그래프(지연 분포, 배치별), 결론.
- **FR-031**: 과제 8용 실행 묶음: 고른 실행 방식의 엔진(또는 ONNX) 파일, 입력 규약 버전, 원본 모델 해시, 엔진 생성 환경. 과제 8은 이 묶음만 읽는다.

**심화**

- **FR-040**: INT8 엔진. 보정 표본은 학습 기간에서만 뽑는다(설정의 표본 수, 씨앗 고정). FP16 대비 지연·오차·시험 MAE 변화를 낸다.
- **FR-041**: 동시 적재 측정: 서비스 구성(예측 1 + 오토인코더 3 + 분류기)을 한 프로세스에 올린 총 메모리와 배치 1 지연을 잰다. 로컬 LLM 크기 가정별(1B·3B·7B, 4비트) 남는 메모리와 가능한 조합 표를 낸다.

**운영·재현**

- **FR-050**: 모든 단계를 설정 파일과 명령으로 다시 실행할 수 있다. 엔진은 보드·TensorRT 버전에 묶이므로 생성 환경을 기록하고, 버전이 바뀌면 다시 만든다.
- **FR-051**: 측정은 과제 3·4 학습이 돌지 않을 때 한다. 시작 전에 우리 학습 프로세스가 있는지 확인하고, 있으면 거부한다.

### Key Entities

- **변환 기록**: 모델, 형식(ONNX / FP16 / INT8), 파일·해시, 원본 해시, 도구 버전, 성공 여부·오류
- **측정 기록**: 실행 방식, 모델, 배치, 워밍업·반복, 지연 통계, 메모리, 전력·에너지·온도, 측정 조건, 시각
- **결과 차이 기록**: 실행 방식, 모델, 표본 수, 원 단위 차이 통계, 바뀐 비율, 판정
- **실행 묶음(과제 8용)**: 고른 실행 방식, 엔진·ONNX 파일, 입력 규약 버전, 원본 모델 해시, 생성 환경

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 변환 후 CO₂ 예측 차이가 시험 표본 전체에서 **최대 1ppm 이하**다(FP16 기준). 넘는 경우 그 표본과 원인이 기록된다.
- **SC-002**: 분류 결과가 바뀐 비율이 **0.1% 이하**다.
- **SC-003**: 모든 측정 결과에 측정 조건(25W, 클럭 고정 안 함, 워밍업·반복, 배치, 온도, 다른 GPU 사용 여부, 소프트웨어 버전)이 붙는다.
- **SC-004**: 실행 방식 4종 × 변환 대상 모델 × 배치 3종 표가 빈칸 없이 채워진다. 지원되지 않는 칸은 사유가 적힌다.
- **SC-005**: 같은 측정을 다시 했을 때 p95가 ±20% 안에서 재현된다.
- **SC-006**: 과제 8이 쓸 실행 방식이 근거(지연·메모리·전력·결과 차이)와 함께 하나로 정해진다.
- **SC-007**: 보고서에 생각해 볼 점 3개의 답이 측정 숫자와 함께 있고, 결과마다 해석이 붙는다(헌법 VII).

## Assumptions

- 변환 대상은 과제 3·4·5의 최종 모델 묶음이다. 과제가 끝나지 않은 모델은 끝난 뒤 측정한다.
- pip TensorRT 11.4가 보드에서 동작한다고 가정하고 시작하되, 첫 작업에서 확인한다. 동작하지 않으면 관리자에게 JetPack TensorRT 설치를 요청한다(사용자 확인 필요).
- 클럭 고정과 전력 모드 변경은 권한이 없어 하지 않는다. 결과는 "25W, 동적 클럭" 조건의 값이다.
- 로컬 LLM의 크기와 런타임은 아직 정해지지 않았다. 심화 2는 크기 가정(1B·3B·7B, 4비트)으로 추정하고, 실제 LLM이 정해지면 다시 잰다.
- 지연은 모델 실행만 잰다. 서비스 전체 주기(데이터 조회·전처리·발행) 시간은 과제 8에서 잰다.
- 측정 시간에 다른 계정(t2)의 GPU 사용을 통제할 수 없다. 기록하고, 경합이 있으면 다시 잰다.
