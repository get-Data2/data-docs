## R1. 사용 여부 정답의 출처

- **Decision**
  - 학습·검증·시험 정답은 **일정 기반**이다.
    - 실습실·사무실: 고정 일과표(`config/analysis.yaml` `schedule`), 일정 중 칸 = 사용중, 공휴일·주말 = 비어있음
    - 회의실: 추정 예약(`var/forecast/booking_estimated.parquet`) 구간 = 사용중. 설정에 실제 예약 CSV가 있으면 그것을 쓴다
  - 칸마다 출처(timetable, booking_estimated, booking_file)를 남긴다.
  - **최종 판정 기준은 직접 관찰**이다. 관찰은 평가에만 쓰고 학습에는 쓰지 않는다.
- **Rationale**
  - README가 정답을 일정에서 만들라고 한다. 과거 10개월은 관찰할 수 없으므로 일정이 유일한 대량 정답이다.
  - 일정은 실제와 다르다. 과제 2 진단에서 실습실 24일, 사무실 52일이 어긋났다. 그래서 관찰로 일정 정답의 오류를 먼저 잰다(US1).
  - 회의실 추정 예약은 CO₂에서 만들었다. 그래서 회의실을 일정 기반으로 평가하면 "CO₂로 CO₂를 맞히는" 순환이다. 회의실 판정은 관찰로만 한다.
- **Alternatives**
  - 관찰만으로 학습: 양(목표 20시간 ≈ 240칸)이 너무 적어 기각했다.
  - CO₂ 상승 규칙으로 정답 만들기: 입력과 같은 신호라 순환이 돼 기각했다.

## R2. 직접 관찰 계획과 기록 방식

- **Decision**
  - **기록 형식**: `data/observations.csv`. 열은 `space_id, start, end, state, people, observer, note`이고 시각은 KST다. 공개 저장소에 올리지 않는다(`data/`는 git 제외, 이름 대신 관찰자 머리글자).
  - **기록 보조**: `state observe <공간> occupied|empty [--people N] [--note ...]`로 상태 전환을 한 줄씩 기록한다. 직전 열린 구간은 자동으로 닫힌다. `state observe <공간> stop`으로 닫고, `--status`로 진행률을 본다.
  - **목표량**(제안, 사용자가 일정 결정)
    - 공간별 수업일 2일 이상, 총 20시간 이상
    - 일정 경계(09:00, 11:30, 13:00, 18:00) ±30분을 공간별 4회 이상 포함. 전환 직후 오판(Q1)을 재기 위해서다
    - 회의실은 회의 2회 이상과 빈 시간 2시간 이상
    - 가능하면 인원 수(Q2)
  - **기간**: 실시간 수집 기간(2026-10-20 ~). 평가 전에 `analysis extract`로 사본을 갱신하고 공간 시계열을 다시 만든다.
- **Rationale**
  - 확인 기준 1은 "직접 관찰한 시간대 기준"이다. 기록이 번거로우면 모이지 않으므로 명령 한 줄로 남기게 한다.
  - 전환 시각을 포함해야 가장 많이 틀리는 상황(입실·퇴실 직후)을 잴 수 있다.
- **Alternatives**
  - 종이 기록 후 수기 입력: 시각 오차가 커서 기각했다(1분 단위가 필요).
  - 카메라: 개인정보 문제와 권한 때문에 기각했다.

## R3. 출입문 센서(WS301)를 보조 신호로 쓸 수 있나

- **Decision**: 정답이나 입력으로 쓰지 않고, **관찰 기록 점검용 보조 지표**로만 쓴다.
  - 관찰 구간 중 "비어있음"인데 문 열림이 있으면 기록 확인 대상으로 표시한다.
  - 오류 분석에서 "문 열림 직후" 칸의 오류율을 따로 본다.
- **Rationale**
  - 문 센서는 열림·닫힘 때만 보고한다. 평소에는 18시간마다 생존 보고만 한다(과제 1 실측). 그래서 "사람이 방 안에 있다"를 직접 알려 주지 않는다. 문을 열어 둔 채 수업하면 신호가 없다.
  - 과제 1 장비 현황에서 문 센서 2대는 "판단 보류"(수신 확인 부족)였다. 신뢰성도 확인되지 않았다.
  - 입력에 넣으면 센서 3종만 쓰는 다른 공간(회의실)과 특징이 달라져 심화 1(처음 보는 공간)과 맞지 않는다.
- **Alternatives**: 문 열림으로 정답 만들기는 위 이유로 기각했다.

## R4. 환기 경보 양성 정의와 "이미 초과" 제외

- **Decision**
  - 칸 t의 라벨은 다음과 같다.
    - **양성**: CO₂(t) < 1,000이고, (t, t+30분]에 관측된 CO₂ 최댓값 ≥ 1,000
    - **음성**: CO₂(t) < 1,000이고, 30분 안 최댓값 < 1,000
    - **이미 초과**: CO₂(t) ≥ 1,000. 학습·평가에서 뺀다
    - **판단 불가**: (t, t+30분] 관측이 모자람(관측 칸 50% 미만). 뺀다
  - CO₂(t)는 공간 대표값의 관측값이다(과제 2 공간 5분 시계열, 관측 칸만).
- **Rationale**
  - 이미 넘은 칸을 양성에 넣으면 "현재 ≥ 1,000"만으로 상당수를 맞힌다. 그러면 재현율이 "미리 알려 주는 능력"이 아닌 "이미 넘은 것을 보는 능력"을 재게 된다(해결할 것 1).
  - 실습실은 수업 시간의 83%가 1,000ppm을 넘는다(과제 2). 이 칸들을 넣으면 양성 비율도 크게 부풀어 README의 1~2% 전제와 달라진다.
- **Alternatives**: 초과 시점을 음성으로 두기는 "넘었는데 경보 없음"을 정답으로 가르쳐 모델을 혼란시켜 기각했다.

## R5. 입력 특징

- **Decision**: 특징은 학습·서비스 공통 전처리(`src/preprocess/`, 과제 8 계획)가 만든 공간 5분 시계열 위에서 만든다. 관측 칸만 쓰고 빈 칸은 앞으로 채우며 관측 표시를 둔다.

  | 묶음 | 특징 | 사용 여부 | 환기 경보 |
  |---|---|---|---|
  | `level` | CO₂·온도·습도 현재값(공간 정규화) | ✓ | ✓ |
  | `delta` | 5·15·30분 변화량(CO₂·온도·습도) | ✓ | ✓ |
  | `shape` | 30분 기울기(선형 회귀), 30분 이동 표준편차, 30분 최소 대비 현재 | ✓ | ✓ |
  | `obs` | 최근 30분 관측 비율, 마지막 관측 뒤 시간 | ✓ | ✓ |
  | `time` | 시각·요일 sin·cos, 공휴일 | ✗(누수 실험만) | ✓ |
  | `schedule` | 일정 상태, 다음 일정 변화까지 남은 시간 | ✗(누수 실험만) | ✓ |

- **Rationale**
  - 사용 여부: 정답이 일정에서 나왔는데 일정·시각을 넣으면 모델은 센서 대신 "몇 시인가"로 맞힌다. 일정 기반 성적은 좋아지지만, 일정과 실제가 다른 날(휴강·주말 사용)에는 일정을 그대로 베껴 틀린다. 이것을 누수 실험(`with_schedule`)으로 보인다(해결할 것 2, SC-006).
    시각·요일은 일정의 대리 변수라 같이 뺀다.
  - 환기 경보: 정답은 미래 CO₂에서 나오므로 일정·시각이 누수가 아니다. 미리 알 수 있는 정보(곧 수업 시작)라 선행 경보에 도움이 된다.
- **Alternatives**: 과제 3처럼 원시 창을 신경망에 넣기는 해석이 어렵고 트리 모델과 비교하기 어려워 기각했다(MLP 후보는 위 특징 벡터를 받는다).

## R6. 분류기 후보와 선택

- **Decision**
  - 후보는 세 가지다. 모두 클래스 가중(`balanced`)으로 불균형을 다룬다.
    - **HistGradientBoosting**(scikit-learn 1.9.1, aarch64 설치 가능 확인): 기본
    - **로지스틱 회귀**: 표준화 특징, 해석용 기준
    - **작은 MLP**(PyTorch, 은닉 64 × 2): 과제 7 변환 대상
  - 하이퍼파라미터 격자는 작게 둔다(트리 깊이·학습률 각 3개, MLP 은닉 2개).
  - 선택 지표는 검증 macro-F1이고, 1표준편차 안이면 단순한 쪽이다(로지스틱 < 트리 < MLP). 씨앗은 3개다.
  - 선택 결과는 `var/state/selection.json`에 고정한다. 그 뒤에만 시험·관찰 평가가 동작한다(과제 3 R9와 같은 방식).
- **Rationale**
  - 특징이 수십 개인 표 데이터에는 트리 모델이 강하고 CPU로 빠르다.
  - 확인 기준이 F1·macro-F1이므로 선택 지표를 맞춘다.
  - MLP 후보를 두면 과제 7(TensorRT)의 "분류 결과 바뀐 비율 ≤ 0.1%" 확인 대상이 생긴다. 최종이 트리 모델이면 과제 7은 CPU 측정만 한다.
- **Alternatives**: LightGBM·XGBoost는 새 의존성이 늘고 이득 근거가 없어 기각했다.

## R7. 임계값

- **Decision**
  - **환기 경보**: 검증 기간 PR 곡선에서 재현율 ≥ 85%를 만족하는 임계값 중 정밀도가 가장 높은 값을 고른다. 만족하는 값이 없으면 재현율 최대인 값을 고르고 "기준 미달 위험"으로 표시한다.
  - **사용 여부**: 검증 macro-F1 최대 임계값을 고른다.
  - 시험 기간 정보는 쓰지 않는다. 자동 시험으로 확인한다: 시험 기간 값을 바꿔도 임계값이 같아야 한다.
- **Rationale**
  - 확인 기준이 "재현율 85% 이상"이다. 검증에서 그 선을 지키고 남는 자유도로 헛경보를 줄인다(Q3).

## R8. 불균형과 지표

- **Decision**: 정확도와 함께 "항상 음성" 분류기의 정확도를 나란히 보여 준다(양성 1~2%면 약 98%). 주 지표는 다음과 같다.
  - 재현율, 정밀도, F1, macro-F1(양성·음성 F1 평균)
  - PR 곡선과 AP
  - 하루당 헛경보(공간 합)
  - 선행 시간: 경보 시각부터 실제 첫 초과까지의 분 분포
- **Rationale**: 정확도는 다수 클래스에 지배된다. 현장은 "놓친 초과"와 "헛경보 수"로 체감한다.

## R9. 단순 규칙과 과제 3 예측 기반 판정

- **Decision**
  - 단순 규칙(README)
    - 사용 여부: 최근 15분 CO₂ 상승 ≥ 30ppm → 사용중
    - 환기: 현재 CO₂ ≥ 850 → 경보
  - **과제 3 판정**: 모델 묶음(`var/forecast/bundle/`)으로 t의 5~30분 예측을 내고, 그 최댓값 ≥ 1,000이면 경보다. 임계값(1,000 대신 1,000 − δ)은 검증 재현율 85% 기준으로 같은 방식으로 정한다.
  - 같은 시점·같은 지표로 비교한다.
- **Rationale**
  - 생각해 볼 점 Q4: 예측 모델은 30분 궤적을 주므로 판정 근거가 설명된다. 분류기는 이 목적에 맞춰 직접 학습해 경계 근처가 날카로울 수 있다. 숫자로 비교한다.
  - 과제 3 묶음은 과제 3 시험 평가 뒤에 생기므로 이 비교는 그 뒤에 한다.

## R10. 오류 분석 방법

- **Decision**
  - **상태 전환 기준 정렬**: 전환 시각(관찰 전환, 없으면 일정 경계) 뒤 0~60분을 5분 단위로 나눠 오류율을 구한다. 퇴실 직후 "사용중" 오판 지속 시간과 입실 직후 "비어있음" 오판 지속 시간을 뽑는다(Q1).
  - **인원별 재현율**: 관찰 인원 1~3명, 4~10명, 그 이상(Q2). 공간 부피 차이는 과제 2의 공간별 CO₂ 상승 속도로 설명한다.
  - **상위 혼동 상황 3개**: 시간대 × 공간 × 상황 조합 중 오류 수 상위. 사례 그래프를 그린다.
  - **환기 헛경보**: 하루당 수와 그 시각대. 정밀도가 낮을 때 생기는 알림 피로를 해석한다(Q3).

## R11. 심화

- **처음 보는 공간**(심화 1)
  - 공간 하나를 학습·검증·정규화 통계에서 빼고(과제 3 R11과 같음) 남은 두 공간으로 학습한다. 뺀 공간의 시험 기간·관찰 구간을 평가한다.
  - 비교 기준은 같은 설정을 세 공간 모두로 학습한 모델이다. 특징은 공간 정규화를 합친 통계로 바꾼다.
- **노쇼·예약 없는 사용**(심화 2)
  - 노쇼: 예약 시작 뒤 15분 동안 추정 사용 여부가 계속 비어있음
  - 예약 없는 사용: 예약 밖에서 추정 사용중이 15분 이상 이어짐
  - 시간 기준은 설정에 둔다.
  - 검증 자료는 관찰 기록(그리고 실제 예약 CSV가 생기면 그것)뿐이다. 추정 예약은 CO₂에서 만들었으므로 "추정 예약 vs 추정 사용 여부" 비교는 순환이다. 이것을 성능으로 보고하지 않고 동작 예시로만 쓴다.

## R12. 실행 환경과 메모리

- **Decision**
  - 트리·선형 모델은 CPU로 돈다. MLP는 GPU를 쓸 수 있으면 쓰되, 작아서 CPU로도 충분하다.
  - 특징 표는 학습 기간 3공간 약 13만 칸 × 약 40열 float32 ≈ 20MB다. 학습·평가 최대 메모리 목표는 1GB다(SC-007의 2GB 안).
  - 학습 실행은 과제 3 실험이 끝난 뒤 한다(보드 메모리를 다른 계정 프로세스와 공유).
