# Research: 사전학습 모델 비교 (과제 6)

각 항목은 Decision(결정) / Rationale(이유) / Alternatives(검토한 대안) 순서다. 기준일은 2026-10-21이다.
"구현 때 확인"이라고 적은 사항은 설치·다운로드 뒤 T00x 작업에서 실측으로 확정한다(지금은 과제 3 학습이 GPU를 쓰는 중이라 설치·실행하지 않음).

## R1. 후보 모델

- **Decision**
  - **기본**: Chronos-Bolt `tiny`·`mini`·`small`(약 9M·21M·48M 파라미터)
    - 분위수 9개(10~90%)를 한 번에 낸다.
    - 패키지 `chronos-forecasting` 2.3.2(aarch64 설치 가능 확인, 2026-10-21 dry-run)
  - **심화 1(공변량)**: Chronos-2
    - 과거 공변량과 미래에 알려진 공변량을 함께 받는 모델로 알려져 있다.
    - 같은 패키지의 지원 여부와 입력 형식을 구현 때 확인한다.
    - 지원되지 않으면 공변량을 받는 다른 공개 모델(Moirai 계열)을 검토한다.
  - TimesFM은 보조 후보다. 추가 의존성이 커 기본 범위에서는 뺀다.
- **Rationale**
  - README가 Chronos 계열을 예로 든다.
  - Bolt는 직접 분위수를 내서 빠르다. 크기 3종이면 "크기 대비 정확도·비용"을 한 표에서 볼 수 있다.
- **Alternatives**: 원조 Chronos(T5)는 표본을 많이 뽑아 분위수를 만들어 보드에서 느리다. 비교 열 하나로만 둘 수 있다.

## R2. 가중치 고정과 오프라인 재실행

- **Decision**
  - 설정에 HuggingFace 저장소 이름과 **리비전(커밋 해시)**을 고정한다. `pretrained fetch`로 `var/pretrained/hf/`에 받는다.
  - 받은 파일의 sha256, 라이선스, 파라미터 수를 `var/pretrained/models.json`에 쓴다.
  - 이후 실행은 `HF_HUB_OFFLINE=1`로 한다.
- **Rationale**: 저장소의 기본 브랜치가 바뀌면 결과를 재현할 수 없다. 보드 외부망은 와이파이라 끊길 수 있다.

## R3. 컨텍스트 만들기와 빈 칸

- **Decision**
  - 과제 2 공간 5분 시계열에서 관측 칸(`filled=False`)만 쓴다. t0까지(포함)의 값으로 정해진 길이의 컨텍스트를 만든다.
  - 빈 칸은 **NaN 그대로** 넘긴다. Chronos 계열은 컨텍스트의 NaN을 결측으로 처리한다(구현 때 실측 확인).
  - NaN을 받지 못하면 앞으로 채우고(과제 3 R4와 같은 인과적 처리) 그 사실을 기록한다.
  - 컨텍스트 관측 비율이 `min_context_obs`(기본 0.1) 미만이면 예측 불가로 둔다. 그 행은 현재값 유지로 대체한다(과제 3 규칙).
- **Rationale**
  - 과제 2 보간 칸은 결측 뒤쪽 값(t0 이후일 수 있음)을 써서 누수가 된다.
  - 회의실(10분 주기)은 칸의 절반이 비어 있다. 결측을 그대로 주는 편이 모델이 아는 형식이다.
- **Alternatives**: 10분 간격으로 다시 모으기는 공간마다 간격이 달라져 비교가 어려워 기각했다.

## R4. 예측 형식과 지평

- **Decision**
  - 예측 길이는 12칸(60분)이다. 지평 5·15·30·60분은 1·3·6·12번째 칸이다.
  - 점 예측은 중앙값(50%)이다(MAE에 맞는 값).
  - 분위수는 10·50·90%를 저장한다(전체 9개 중 필요분). 정렬 후 사용하고, 0 미만은 0으로 자른다.
  - 출력은 `var/pretrained/preds/<모델>__<컨텍스트>__<기간>.parquet`이다.
- **Rationale**: 과제 3 평가 함수와 같은 키(공간, item, t0, horizon_min)로 결합한다.

## R5. 선택 절차(누수 방지)

- **Decision**
  - 검증 기간(2026-04-02 ~ 05-09)에서 과제 3과 같은 규칙으로 표본 t0를 뽑는다(CO₂, t0 관측, 60분 뒤가 기간 안).
  - 그 표본에서 모델 크기 × 컨텍스트 길이(1시간·4시간·1일·1주) 조합의 MAE를 낸다.
  - 앙상블 가중치(심화 2)도 검증 예측으로 고른다.
  - `pretrained select`가 `var/pretrained/selection.json`을 해시와 함께 고정한다. 그 뒤에만 시험 평가를 허용한다(과제 3 `require_selection`과 같은 방식).
  - 시험 평가는 "선택된 크기·컨텍스트" 한 조합이다. 다른 크기(tiny·mini·small)의 시험 결과는 비용 비교용으로 함께 내되, 선택에는 쓰지 않았음을 표에 적는다.
- **Rationale**: 사전학습 모델은 학습이 없지만 크기·컨텍스트·가중치 선택이 곧 하이퍼파라미터 선택이다. 이를 시험 기간으로 하면 누수다.

## R6. 예측 구간 평가

- **Decision**: 공간 × 지평 × (전체·사용 시간대)마다 다음을 계산한다.
  - 적중률 = P10 ≤ 정답 ≤ P90인 비율
  - 아래 이탈 = 정답 < P10, 위 이탈 = 정답 > P90
  - 평균 폭 = P90 − P10(ppm)
  - 보정 곡선: 명목 분위수 0.1~0.9 대비 실제 정답 ≤ q 비율
- **해석 규칙**: 적중률이 80%보다 낮으면 과신(구간이 좁음), 높으면 과소신(구간이 넓음)이다. 이탈 방향으로 상승 놓침/하락 놓침을 구분한다.
- **Rationale**: README의 "80%가 구간 안"을 공간·순간별로 나눠 봐야 원인을 설명할 수 있다.

## R7. 비용 측정 방법

- **Decision**
  - 측정 대상: 모델 × 장치(GPU·CPU) × 배치(1, 3)
    - 입력은 실제 시험 기간 컨텍스트(선택된 길이) 중 무작위 고정 표본이다.
    - 워밍업 10회 뒤 100회를 반복하고 평균·p95(ms)를 낸다.
    - GPU는 매 회 동기화한다.
  - 메모리: 프로세스 최대 RSS(`resource`), GPU 최대 할당(`torch.cuda.max_memory_allocated`), 측정 전후 보드 사용량(`tegrastats` RAM).
  - 전력: 측정 구간 동안 `tegrastats --interval 100`을 함께 띄워 VDD_IN·VDD_CPU_GPU_CV 평균과 GR3D(GPU 사용률)를 기록한다. 측정 전 30초 유휴 구간도 기록해 차이를 낸다.
  - 측정 조건
    - 전력 모드(`nvpmodel -q`: 25W)
    - **클럭 고정 안 함**(`jetson_clocks`는 sudo 필요)
    - 동시 실행 프로세스: `ps`로 다른 GPU·고부하 작업 기록, 관찰된 t2 프로세스 포함
  - 과제 3 최종 모델(`var/forecast/bundle/`)도 같은 하네스로 잰다.
  - 하네스는 과제 7이 재사용할 수 있게 `src/pretrained/bench.py`에 둔다.
- **Rationale**: 확인 기준 2번(시간·메모리)과 과제 7의 측정 조건 요구가 같다.

## R8. 정보 차이 분해(생각해 볼 점 Q1)

- **Decision**: 두 차이를 나눠 보고한다.
  1. 과제 3 D2 단계의 검증 결과(`stages.json`): `[sensors]` vs `[sensors+time+space+schedule]` — 시간·공간·일정 정보의 몫
  2. 과제 3 `[sensors]` 모델 vs 사전학습(CO₂만): 온습도 입력 + "우리 데이터로 학습"의 몫

  가능하면 과제 3의 `[sensors]` 설정에서 습도·온도를 뺀 CO₂만 모델을 하나 더 학습해 2번을 다시 나눈다(선택, 과제 3 실험 종료 뒤).
- **Rationale**: 새 실험을 최소화하고 이미 있는 검증 결과로 답한다. 검증 기간 값이므로 선택 누수와 무관하다(보고용).

## R9. 메모리 예산(생각해 볼 점 Q3)

- **Decision**: 표로 판단한다.
  - 행: OS·데스크톱(관찰), 수집기(관찰), 다른 계정 작업(관찰, 약 1GB), 로컬 LLM(가정), 과제 3·4·5 모델(과제 7 측정), 사전학습 모델(R7 측정)
  - 합계가 7.3GB의 85%(약 6.2GB) 이하인지로 판정한다.
  - LLM 가정 기본값은 "4B급 4비트 약 3GB"이고, 2B·8B 두 경우를 함께 보인다. 실제 크기는 사용자 확인 항목이다.
- **Rationale**: LLM 크기를 모르는 상태에서 판단을 미루지 않고, 조건별 결론을 준다.

## R10. 섞은 예측(심화 2)

- **Decision**
  - 예측: ŷ = w·ŷ_직접 + (1−w)·ŷ_사전학습(중앙값)
  - w는 검증 기간 MAE를 최소로 하는 값이다(0~1, 0.1 간격). 공간 × 지평별 w와 전체 하나의 w 두 방식을 검증에서 비교해 고른다.
  - 직접 학습 모델의 검증 예측은 과제 3 실행 기록의 `val_pred.parquet`(최종 설정, 씨앗 평균)을 쓴다. 사전학습 검증 예측은 R5의 표본을 같은 키로 맞춘다.
- **Rationale**: 두 모델의 오차가 서로 다른 순간에 크면 평균이 이긴다. 가중치를 시험에서 고르면 누수다.

## R11. 공변량 입력(심화 1)

- **Decision**
  - 과거 공변량: 온도·습도(관측만, 빈 칸 NaN)
  - 과거 + 미래 공변량: 하루 시각 sin·cos, 요일 sin·cos, 공휴일, 일과표 상태(과제 3 `forecast.features` 재사용)
  - 같은 모델·같은 컨텍스트에서 공변량 있음/없음을 비교한다.
- **Rationale**: 시간·일과표는 t0에 이미 아는 미래 정보다(과제 3 R6). 같은 특징 함수를 써서 과제 3과 정의를 맞춘다.

## R12. 실행 환경

- **Decision**
  - 패키지는 `.venv`에 `pretrained` extra(`chronos-forecasting`)로 설치한다.
  - GPU 실행은 `tools/pretrained` 래퍼(`tools/forecast`와 같은 sg 처리·환경 변수)로 한다.
  - 정밀도는 GPU bf16 지원 여부를 구현 때 확인한다. Orin은 bf16을 지원하지만 이 torch판의 연산 규격 8.7 지원 경고가 있다.
    - fp32와의 결과 차이를 함께 기록한다.
  - 과제 3·4 학습 중에는 예측 계산만 하고, 비용 측정은 하지 않는다.
- **Rationale**: 측정이 다른 작업과 겹치면 지연·전력 수치가 오염된다.
