# Feature Specification: 상시 추론 서비스 (과제 8)

**Feature Branch**: `008-inference-service`

**Created**: 2026-10-21

**Status**: Ready for plan

**Input**: User description: "과제 8 상시 추론 서비스 (README '과제 8' 전체 + 심화 B 2개). 매분 공간마다 60분 예측과 바로 쓸 수 있는 경보,
이상 여부·점수·원인 센서·규칙 경보, 사용 여부·환기 선제 경보를 계산한다. MQTT 발행(새 구독자도 최신값)과 조회 API로 제공하고,
학습과 같은 전처리를 쓰며, 데이터 끊김·계산 실패·재부팅에 버틴다. 결과 형식 문서를 남긴다.
확인 기준: 12시간 무중단, 수집기 10분 정지 시 끊김 경보와 복귀, 조회 API로 공간별 예측·이상·상태, 결과 형식 문서.
심화: 예측 기반 환기·냉난방 제어 규칙과 지난 1주 적용 시 1,000ppm 초과 시간 감소 추정, 서비스 자기 성능 감시."

## 배경 (2026-10-21 기준)

- **입력**: 과제 1 수집기(`wonil-collector`)가 MySQL `cf_u36_d3.measurement`에 매분 실시간 측정값을 쌓는다(2026-10-20 16:33~).
  서비스는 이 표에서 **최근 창만** 읽는다. 접속 정보는 `.env`(과제 1 `collector.store.connect` 재사용)다.
- **모델 묶음**(각 과제가 만든다)

| 묶음 | 위치 | 내용 | 만드는 과제 |
|---|---|---|---|
| 60분 예측 | `var/forecast/bundle/` | 가중치, 입력 규약(과거 길이·특징 순서), 정규화 통계 | 3 |
| 이상 탐지 | `var/anomaly/bundle/` | 공간별 오토인코더, 규칙 파라미터, 임계값, 분위수 표 | 4 |
| 상태 추정 | `var/state/bundle/` | 사용 여부·환기 선제 경보 분류기, 임계값 | 5 |
| 실행 방식 | 과제 7 결과 | TensorRT 엔진 파일이 있으면 그것, 없으면 PyTorch | 7 |

- **전처리**: 학습 데이터는 과제 2 규칙으로 만들었다.
  - 축 A 오류 코드 제거
  - 센서 5분 칸 평균
  - 공간 대표값 = 센서 중앙값(복도 센서 제외)
  - 입력은 관측 칸만 쓰고 빈 칸은 앞으로만 채움(과제 3)

  서비스는 **같은 함수**로 이 전처리를 해야 한다.
- **대상 공간**: 실습실(lab), 사무실(office), 회의실(meeting). 회의실은 10분 주기 센서 1대다.
- **실행 환경**
  - 보드: Jetson Orin Nano Super, RAM 7.3GB(CPU·GPU 공유), sudo 없음
  - 상시 실행: systemd 사용자 서비스 + `Linger=yes`(과제 1에서 적용)
  - 같은 보드에 수집기, 다른 계정(t2) 작업, 향후 로컬 LLM이 함께 돈다.
  - GPU 그룹(video·render)은 2026-10-21에 추가됐다. 사용자 서비스 관리자가 그 뒤 다시 시작돼야(재부팅) 서비스에서 GPU가 보인다.
- **제공 경로 미확정**
  - 팀 MQTT 브로커에 **발행할 권한이 있는지 확인하지 않았다**(과제 1은 구독만 함).
  - 조회 API를 열 주소·포트도 정해지지 않았다.

## 용어

| 용어 | 뜻 |
|---|---|
| 주기 | 매분 0초 + 여유(기본 20초)에 한 번 도는 계산. 공간마다 결과 한 묶음을 낸다 |
| 닫힌 칸 | 끝 시각이 지난 5분 칸. 아직 진행 중인 칸은 "부분 칸" |
| 바로 쓸 수 있는 경보 | 예측에서 바로 읽은 판단. 예: "23분 뒤 CO₂ 1,000ppm 초과 예상" |
| 규칙 경보 | 데이터 끊김 · 값 고정 · 범위 밖 |
| 신선도 | 결과가 기댄 마지막 관측의 나이(분) |
| 경보 상태 | `none` → `active`(첫 발생) → `active`(재알림) → `cleared`(해제) |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 매분 공간별 최신 판단을 계산한다 (Priority: P1)

운영자는 사람이 손대지 않아도 매분 공간마다 예측·이상·상태가 새로 계산되기를 원한다.

**Why this priority**: 해결할 것 1번이며 서비스의 존재 이유다.

**Independent Test**: 서비스를 켜 두면 매분 공간마다 결과 한 묶음(예측 12칸 × 2항목, 1,000ppm 초과 예상 시각, 이상 점수·원인, 규칙 경보, 사용 여부, 환기 선제 경보)이 생기고 처리 시간이 기록된다.

**Acceptance Scenarios**:

1. **Given** 수집기가 정상, **When** 한 주기가 돌면, **Then** 세 공간마다 다음 결과가 나온다.
   - 60분 예측: CO₂·온도, 5분 간격 12칸
   - "몇 분 뒤 1,000ppm 초과" 판단: 없으면 null
   - 이상 판단: 이상 여부·점수(0~1 분위수)·원인 센서 상위 3
   - 규칙 경보: 끊김·값 고정·범위 밖
   - 상태: 사용 여부(확률 포함)·환기 선제 경보(30분 안 1,000ppm)
2. **Given** 한 주기, **When** 처리 시간을 보면, **Then** 단계별(읽기·전처리·추론·발행) 시간이 기록되고 주기 전체가 20초 이내다.
3. **Given** 모델 묶음, **When** 서비스가 시작하면, **Then** 묶음 형식·입력 규약 버전·정규화 통계·데이터 해시를 검사한다. 맞지 않으면 그 판단만 끄고 이유를 상태에 표시한다(서비스 전체는 돈다).

---

### User Story 2 - 다른 팀이 MQTT와 조회 API로 가져다 쓴다 (Priority: P1)

대시보드 팀, 로컬 LLM 에이전트, 냉난방 제어 시스템은 결과를 구독하거나 필요할 때 물어본다.

**Why this priority**: 해결할 것 2번과 확인 기준 3번.

**Independent Test**: 새 구독자가 접속하자마자 공간별 최신 결과를 받는다. 조회 API로 "회의실 30분 뒤 CO₂"를 물으면 값과 단위·근거 시각이 온다.

**Acceptance Scenarios**:

1. **Given** 발행 중인 서비스, **When** 새 MQTT 구독자가 `team2/inference/v1/#`을 구독하면, **Then** 보존(retained) 메시지로 공간·종류별 최신 결과를 바로 받는다.
2. **Given** 조회 API, **When** `GET /v1/spaces/meeting/forecast?minutes=30`을 부르면, **Then** 30분 뒤 CO₂·온도 예측, 단위, 기준 시각, 신선도, 모델 버전이 JSON으로 온다.
3. **Given** 조회 API, **When** 공간별 이상·상태를 물으면, **Then** 최신 주기의 결과가 온다. 없는 공간은 404, 판단이 꺼져 있으면 이유를 담은 응답이 온다.
4. **Given** 발행 실패(브로커 끊김), **When** 다음 주기가 오면, **Then** 재접속해 최신 결과를 다시 보존 발행한다. 계산은 멈추지 않는다.

---

### User Story 3 - 학습 때와 똑같은 전처리 (Priority: P1)

분석가는 서비스가 학습과 다른 입력을 모델에 넣지 않는다는 보장을 원한다.

**Why this priority**: 해결할 것 3번. 전처리가 다르면 모델은 본 적 없는 입력을 받아 조용히 틀린다.

**Independent Test**: 같은 원본 구간을 학습 경로(과제 2·3 함수)와 서비스 경로로 처리하면 모델 입력 텐서가 같다.

**Acceptance Scenarios**:

1. **Given** 과거의 한 시각, **When** 서비스 경로가 MySQL 원본에서 모델 입력을 만들면, **Then** 학습 경로(과제 2 사본 → 과제 3 배열)가 만든 입력과 원 단위로 같다(허용 오차 1e-4).
2. **Given** 서비스 전처리 코드, **When** 보면, **Then** 축 A·5분 칸·공간 중앙값·앞으로 채우기를 별도로 다시 짜지 않고 학습과 같은 함수를 부른다.
3. **Given** 막 시작된 5분 칸(부분 칸), **When** 입력을 만들면, **Then** 정해진 규칙(research R3)대로 처리한다. 학습 때와 다른 칸 정의를 쓰지 않는다.

---

### User Story 4 - 장애에 버틴다 (Priority: P1)

운영자는 데이터 일부 끊김, 계산 실패, 재부팅이 있어도 서비스가 스스로 돌아오기를 원한다.

**Why this priority**: 해결할 것 4번, 확인 기준 1·2번(헌법 VI).

**Independent Test**
- 수집기를 10분 멈추면 끊김 경보가 나고, 다시 켜면 정상으로 돌아온다.
- 일부러 한 주기를 실패시켜도 다음 주기는 정상이다.
- 재부팅 뒤 자동으로 시작한다.

**Acceptance Scenarios**:

1. **Given** 수집기 정지(`systemctl --user stop wonil-collector`), **When** 데이터가 장치 기대 주기의 끊김 기준(과제 1: max(10분, 주기×2))을 넘기면, **Then** 해당 공간·장치에 `data_gap` 경보가 발행된다. 예측은 "신선도 낮음" 표시와 함께 계속되거나 정해진 한도(research R6)를 넘으면 멈추고 이유를 표시한다.
2. **Given** 수집기 재시작, **When** 새 데이터가 들어오면, **Then** 끊김 경보가 `cleared`로 바뀌고 다음 주기 결과가 정상이다.
3. **Given** 한 주기 중 예외(DB 시간 초과, 모델 오류), **When** 다음 주기, **Then** 정상 계산된다. 실패는 기록되고 상태 토픽에 남는다.
4. **Given** 보드 재부팅, **When** 부팅이 끝나면, **Then** 사용자 로그인 없이 서비스가 시작돼 첫 결과를 낸다(목표: 부팅 뒤 3분 이내).
5. **Given** 12시간 가동, **When** 기록을 보면, **Then** 빠진 주기 수, 주기별 처리 시간 분포, 경보 내역, 장애 시험 결과가 나온다.

### User Story 5 - 결과 형식 문서 (Priority: P1)

다른 팀 개발자는 이 문서만 보고 결과를 쓴다.

**Why this priority**: 해결할 것 5번, 확인 기준 4번, 최종 제출물 "결과 형식 문서"(재사용성 10%).

**Independent Test**: 문서만 보고 MQTT 구독 예제와 API 호출 예제가 그대로 동작한다.

**Acceptance Scenarios**:

1. **Given** 결과 형식 문서, **When** 읽으면, **Then** 토픽·필드·단위·값 범위·예시 메시지·API 엔드포인트·응답 예시·오류 코드·버전 정책·경보 재발송 규칙이 있다.
2. **Given** 문서의 예제 명령, **When** 실행하면, **Then** 실제 응답이 문서 예시와 같은 형식이다.

### User Story 6 - 경보를 알맞게 보낸다 (Priority: P2)

운영자는 같은 고장으로 매분 알림을 받고 싶지 않지만, 계속되는 문제를 잊고 싶지도 않다.

**Why this priority**: 생각해 볼 점 Q2. 알림이 너무 잦으면 운영자는 알림을 끈다(과제 4).

**Acceptance Scenarios**:

1. **Given** 같은 경보가 매분 판정됨, **When** 발행하면, **Then** 상태가 바뀔 때(`active`·`cleared`)만 경보 토픽에 이벤트를 낸다. 계속되면 정해진 간격(기본 30분)으로 재알림한다.
2. **Given** 경보가 깜빡임(경계값 근처), **When** 판정하면, **Then** 해제에 지속 조건(기본 연속 3주기 정상)을 둬 깜빡임을 줄인다.

---

### User Story 7 - 심화(B) (Priority: P3)

1. **제어 규칙**: 예측으로 "30분 안 1,000ppm 초과 예상 시 환기 시작", "사용 예상 + 온도 예측이 쾌적 범위를 벗어나면 냉난방 시작" 같은 규칙을 설계한다.
   지난 1주 데이터에 적용했을 때 1,000ppm 초과 시간이 얼마나 줄었을지 추정한다. 환기 효과 모형과 가정을 명시한다.
2. **자기 성능 감시**: 60분 뒤 실제 값이 들어오면 그때의 예측을 채점하고(지평별 MAE 이동 창), 과제 3 시험 MAE 대비 정해진 배수를 넘으면 `model_drift` 경보를 낸다.

### Edge Cases

- **부분 칸**: 지금 진행 중인 5분 칸은 1~2분치만 있다. 쓰면 칸 평균이 학습 때와 다르다(Q1). 닫힌 칸만 쓰는 것이 기본이다(research R3).
- **회의실 10분 주기**: 닫힌 칸의 절반이 비어 있는 것이 정상이다. 끊김으로 오판하지 않는다(과제 1 기대 주기 사용).
- **DB 느림·끊김**: 읽기 시간 초과(기본 10초) 시 그 주기는 직전 결과의 신선도만 갱신하고 실패를 기록한다.
- **모델 묶음 없음**(과제 5·7 미완료 등): 그 판단만 `unavailable`로 내고 나머지는 계속한다.
- **시계**: 기준 시각은 과제 1과 같은 `nsTime` 기반 `ts`다. 보드 시계와 측정 시각의 차이가 크면(5분 이상) 상태에 경고한다.
- **GPU 없음**: 사용자 서비스 관리자에 그룹이 반영되지 않았거나 메모리가 부족하면 CPU로 실행한다(결과 동일, 지연만 증가).
- **보존 메시지 정리**: 공간·종류가 없어지면 빈 보존 메시지로 지운다.
- **일과표 경계·공휴일**: 상태 추정과 경보는 과제 2 일과표·공휴일 정의를 그대로 쓴다.

## Requirements *(mandatory)*

### Functional Requirements

**주기 계산**

- **FR-001**: 매분 정해진 초(기본 20초)에 한 주기를 시작한다. 주기가 겹치면 이전 주기가 끝날 때까지 건너뛰고 건너뜀을 기록한다.
- **FR-002**: 주기마다 MySQL에서 최근 창(가장 긴 입력 + 여유, 기본 5시간)만 읽는다. 다음 주기부터는 증분만 읽고 메모리 창을 갱신한다.
- **FR-003**: 공간마다 다음을 계산한다. 단, 묶음이 없는 판단은 `unavailable`이다.
  - 60분 예측(과제 3 묶음)과 1,000ppm 첫 초과 예상 시각
  - 이상 점수·여부·원인 상위 3(과제 4 묶음)
  - 규칙 경보: 끊김·값 고정·범위 밖
  - 사용 여부·환기 선제 경보(과제 5 묶음)
- **FR-004**: 추론 실행 방식은 과제 7 결과를 따른다. 엔진 파일과 검증 기록이 있으면 TensorRT, 없으면 PyTorch(GPU, 안 되면 CPU)다. 실제 쓴 방식을 결과에 기록한다.

**전처리 일치**

- **FR-010**: 서비스 전처리는 학습 경로와 **같은 함수**를 호출한다. 해당 함수는 공통 모듈에 한 번만 정의한다.
  - 과제 2: 축 A, 5분 칸 평균, 공간 중앙값
  - 과제 3: 인과적 배열
- **FR-011**: 기본은 닫힌 칸만 쓰는 것이다. 부분 칸을 쓰는 설정은 두지 않는다(research R3).
- **FR-012**: 학습 경로와 서비스 경로의 입력이 같은지 자동 시험으로 확인한다(US3).

**제공**

- **FR-020**: MQTT 발행: 토픽 `team2/inference/v1/{space}/{kind}`. `kind`는 forecast · anomaly · rules · state · alerts · health다. 보존(retained), QoS 1이다.
  발행 대상 브로커(팀 브로커 / 보드 로컬 브로커)는 설정값이다(research R4).
- **FR-021**: 조회 API(HTTP, JSON): 공간 목록, 공간별 최신 묶음, 예측(분 지정), 이상, 상태, 경보, 서비스 상태, OpenAPI 스키마. 바인딩 주소·포트는 설정값이다.
- **FR-022**: 모든 결과에 다음을 둔다. 형식은 contracts/mqtt.md를 따른다.
  - 스키마 버전, 기준 시각(UTC·KST)
  - 신선도(분), 단위, 모델 묶음 버전·해시, 실행 방식

**장애**

- **FR-030**: 장치별 끊김 판정은 과제 1 기준(max(10분, 기대 주기 × 2), 사건형 장치 제외)을 재사용한다.
- **FR-031**: 한 주기 실패는 기록하고 다음 주기에 다시 시도한다. 공간 하나·판단 하나의 실패는 그 결과만 `error`로 둔다.
- **FR-032**: systemd 사용자 서비스 `wonil-inference`(Restart=always)로 운영하고 재부팅 뒤 자동 시작한다. 설치 스크립트를 제공한다.
- **FR-033**: 주기 기록(시작·끝·단계별 시간·성공/실패·건너뜀), 경보 이력, 장애 시험 기록을 남긴다.
  12시간(또는 지정 기간) 요약 보고서를 명령 하나로 만든다.

**경보 정책**

- **FR-040**: 경보는 상태 기계다(none → active → cleared). 이벤트 발행 시점은 다음과 같다.
  - 상태가 바뀔 때
  - 계속될 때 재알림 간격(기본 30분)마다
  - 해제는 연속 정상 주기(기본 3) 뒤
- **FR-041**: 경보마다 종류, 대상(공간·장치), 시작 시각, 근거 값, 권장 행동(문장), 알림 대상 역할(과제 4 운영 제안)을 담는다.

**심화**

- **FR-050**: 제어 규칙 시뮬레이션: 지난 7일 실데이터에 규칙을 적용한다. 정해진 환기 효과 모형으로 1,000ppm 초과 시간 감소를 추정하고 가정을 표로 낸다.
- **FR-051**: 자기 성능 감시: 예측을 저장해 두고 60분 뒤 채점한다. 지평별 이동 MAE(기본 24시간 창)가 과제 3 시험 MAE의 정해진 배수(기본 2배)를 넘으면 `model_drift` 경보를 낸다.

**운영·문서**

- **FR-060**: 설정은 `config/service.yaml`, 명령은 `infer run | once | status | report | selftest`다.
- **FR-061**: 산출물은 `docs/deliverables/task8/`, 심화는 `docs/advanced/task8/`, 점검은 `docs/tasks/task8-inference-service.md`에 둔다.
  - 산출물 목록: 서비스 v1 운영 기록, 12시간 가동 요약, 결과 형식 문서
- **FR-062**: 서비스 프로세스 메모리 목표는 1GB 이하다(수집기·다른 계정 작업·향후 LLM과 공존).

### Key Entities

- **주기 기록**: 주기 id, 예정·시작·끝 시각, 단계별 시간, 상태(ok·partial·failed·skipped), 오류
- **공간 결과**: 공간, 기준 시각, 신선도, 예측, 초과 예상, 이상, 규칙 경보, 상태, 판단별 가용 여부, 모델 버전
- **경보**: 종류, 공간, 장치, 상태, 시작·마지막 알림·해제 시각, 근거, 권장 행동, 알림 대상
- **모델 묶음 참조**: 과제·경로·입력 규약 버전·해시·실행 방식
- **예측 채점**(심화): 기준 시각, 공간, 항목, 지평, 예측, 실제, 오차

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: **12시간 무중단** 가동 기록이 있다. 예정 주기 720개 중 빠진 주기 0개를 목표로 하고, 빠짐이 있으면 원인을 기록한다.
- **SC-002**: 가동 중 수집기를 10분 멈추면 끊김 경보가 **기준 시간 안**에 발행되고, 다시 켜면 다음 몇 주기 안에 `cleared`와 정상 결과가 나온다.
- **SC-003**: 조회 API로 세 공간의 예측·이상·상태를 받는다. 응답 시간은 p95 200ms 이하다.
- **SC-004**: 새 MQTT 구독자가 접속 1초 안에 공간·종류별 최신 결과를 받는다(보존 메시지).
- **SC-005**: 학습 경로와 서비스 경로의 모델 입력이 같다(자동 시험, 허용 오차 1e-4).
- **SC-006**: 주기 처리 시간 p95가 20초 이하이고, 서비스 메모리가 1GB 이하다.
- **SC-007**: 재부팅 뒤 사용자 로그인 없이 3분 안에 첫 결과를 낸다.
- **SC-008**: 결과 형식 문서만 보고 다른 사람이 구독·조회 예제를 실행할 수 있다(문서 예제를 실제로 실행해 확인).
- **SC-009**: 모든 운영 기록·요약표에 측정 조건(기간, 실데이터, 모델 묶음 버전, 실행 방식, 전력 모드)이 붙는다(헌법 V·VII).

## Assumptions

- 과제 3·4·5 모델 묶음과 과제 7 실행 방식이 준비되는 대로 붙인다. 준비 전에는 해당 판단을 `unavailable`로 둔 채 서비스 뼈대와 장애 대응을 먼저 검증한다.
- 팀 MQTT 브로커 발행 권한은 확인 전이다. 확인은 **사용자 승인 뒤** 시험 토픽 한 번 발행으로 한다. 권한이 없으면 보드 로컬 브로커(amqtt)에 발행하고, 다른 팀은 보드 주소로 구독한다.
- 조회 API는 팀 내부망·Tailscale 주소에서 접근하는 것을 가정한다. 인증은 이번 범위 밖이고 읽기 전용이다. 포트는 사용자 확인 뒤 정한다.
- 일과표는 과제 2 고정 일과표, 회의실 예약은 없음(과제 3 결정)을 그대로 쓴다.
- 냉난방 상태(xflow)는 2026-10-20부터만 있다. 제어 규칙 시뮬레이션은 측정값 기반 가정 모형으로 한다.
