# Research: 상시 추론 서비스 (과제 8)

각 항목은 Decision(결정) / Rationale(이유) / Alternatives(검토한 대안) 순서다. 기준일은 2026-10-21이다.

## R1. 주기 실행 구조

- **Decision**
  - 프로세스 하나에 루프 하나를 둔다. 매분 `:20`초(설정 `cycle.offset_s`)에 주기를 시작한다.
  - 수집기가 2초마다 일괄 기록하고, LoRa 업링크는 수신까지 1초 안팎이다. 20초 여유면 직전 분의 값이 DB에 들어온다.
  - 주기 하나의 단계: 증분 읽기 → 전처리 → 공간별 추론 → 경보 상태 갱신 → 발행·API 저장소 갱신 → 기록
  - 주기가 다음 예정 시각을 넘기면 다음 주기는 건너뛴다(`skipped` 기록). 겹쳐 돌지 않는다.
  - 조회 API는 같은 프로세스의 별도 스레드에서 돈다. 최신 결과는 메모리 저장소(잠금 보호)에서 읽는다.
- **Rationale**
  - 모델을 한 번만 올려 메모리를 아낀다(목표 1GB).
  - API는 계산과 같은 결과를 즉시 돌려준다.
- **Alternatives**
  - cron으로 매분 새 프로세스를 띄우는 방식: 모델 적재가 매분 수 초 걸리고 GPU 초기화(약 0.6GB)가 반복돼 기각했다.
  - 계산과 API를 별도 서비스로 나누는 방식: 결과 공유에 저장소가 더 필요해 기각했다.

## R2. 입력 읽기와 공통 전처리

- **Decision**
  - 시작 시 MySQL에서 최근 `window_h`(기본 5시간 = 과제 3 최대 입력 4시간 + 여유)를 읽는다. 이후 주기마다 `ts > 마지막 ts − 10분`(늦게 도착한 행 보정)만 읽어 메모리 창에 합친다.
  - 전처리는 학습과 같은 함수를 부른다. 현재 학습 코드는 "사본 전체를 한 번에" 처리하는 형태이므로, 행 단위 순수 함수로 꺼내 학습·서비스가 같이 쓰게 정리한다(tasks에 포함). 대상 함수는 다음과 같다.
    - `analysis.quality.apply_axis_a`(축 A)
    - `analysis.series`의 센서 5분 칸·공간 중앙값
    - `forecast.data`의 인과적 채우기·관측 표시·경과 시간
    - `forecast.features`의 시간·일과표 특징
  - 일치 시험: 과거 시각 몇 개를 골라 (a) 과제 2 사본 → 과제 3 배열과 (b) MySQL 원본 → 서비스 경로의 모델 입력 텐서를 비교한다.
- **Rationale**
  - 해결할 것 3번이다. 전처리가 다르면 생기는 일은 다음과 같다.
    - 칸 평균 방식, 중앙값 대상 센서, 오류 코드 제거가 다르면 모델은 학습 때 본 적 없는 분포를 받는다.
    - 그러면 오류 없이 **조용히** 틀린 예측을 낸다.
    - 예: 65535 오류 코드가 남으면 칸 평균이 수만 ppm이 돼 예측과 이상 점수가 동시에 망가진다.
    - 정규화 통계가 다르면 모든 예측이 한쪽으로 치우친다.
  - 코드를 한 곳에 두는 것이 가장 확실한 방지책이다.
- **Alternatives**: 서비스용 전처리를 따로 짜고 문서로 맞추는 방식은 시간이 지나면 어긋나 기각했다.

## R3. 부분 칸(생각해 볼 점 Q1)

- **Decision**: **닫힌 칸만 쓴다.** 주기 시각이 10:03:20이면 마지막 입력 칸은 [09:55, 10:00)이다.
  - 그 결과 예측의 기준 시각 t0는 마지막 닫힌 칸 끝이고, 정보 지연은 최대 5분이다.
  - 출력에는 `t0`와 `computed_at`을 함께 둔다. "지금부터 몇 분 뒤"는 t0 기준으로 계산해 바로 쓰는 값으로 낸다.
  - 규칙 경보 중 끊김·범위 밖은 1분 원본으로 바로 판정한다(지연 없음).
- **Rationale**
  - 부분 칸 평균은 1~2분치라 잡음이 크다.
  - 10분 주기 센서는 부분 칸에 값이 아예 없을 수 있다.
  - 학습 때는 모든 칸이 닫힌 칸이었다. 부분 칸을 쓰면 전처리 불일치(R2)가 된다.
  - 5분 지연은 60분 예측의 쓰임(환기 준비)에 비해 작다.
- **Alternatives**
  - 부분 칸 사용 + 관측 수 표시: 학습에 없던 입력이라 기각했다.
  - 1분 칸으로 다시 학습: 과제 2 분석 간격 결정과 충돌해 기각했다.

## R4. MQTT 발행 대상(확인 필요)

- **현황**: 과제 1 수집기는 팀 브로커를 **구독만** 했다. 발행 권한(ACL)은 확인하지 않았다. 공용 브로커에 발행하는 것은 외부에 영향을 주는 행동이다.
- **Decision**: 발행 대상을 설정 `mqtt.target: team | local`로 둔다.
  1. **확인 절차**: 사용자 승인을 받은 뒤 시험 토픽 `team2/inference/v1/_probe`에 보존 없이(QoS 1, retain false) 한 번 발행한다.
     - 별도 구독 연결로 그 메시지가 돌아오는지 본다.
     - 거부(연결 끊김·PUBACK 실패)되거나 돌아오지 않으면 권한이 없는 것으로 본다.
     - 결과는 점검 문서에 기록한다.
  2. 권한이 있으면 `team`(다른 팀이 같은 브로커에서 구독)이다.
  3. 권한이 없으면 `local`이다.
     - 보드에서 amqtt 브로커를 사용자 서비스로 띄운다. amqtt는 시험용으로 이미 설치돼 있다.
     - 포트와 인증은 설정값이다.
     - 다른 팀은 보드 주소(내부망·Tailscale)로 구독한다.
- **Rationale**: 권한을 모르는 채 공용 브로커에 보존 메시지를 남기면 다른 팀 토픽 공간을 오염시킬 수 있다. 확인 절차와 대안을 둬 어느 쪽이든 확인 기준(새 구독자가 최신값 받기)을 만족한다.
- **토픽 규칙**
  - 접두사는 `team2/inference/v1/`이다. 스키마가 깨지는 변경이 생기면 `v2`로 올린다.
  - 보존 메시지는 공간·종류별 최신 1개다.
  - `alerts`는 상태 변화 이벤트라 보존하지 않는다. 경보의 현재 목록은 보존 토픽 `.../{space}/alerts/active`에 둔다.

## R5. 조회 API 서버

- **Decision**
  - 표준 라이브러리 `http.server.ThreadingHTTPServer` 기반의 작은 JSON 라우터를 쓴다(GET만).
  - OpenAPI 3 스키마는 손으로 쓴 JSON을 `/v1/openapi.json`으로 내보낸다.
  - 바인딩 기본값은 `0.0.0.0:18080`이다(2026-10-21 결정, 아래 결정 기록).
- **Rationale**
  - 읽기 전용·저부하(분당 수 회)라 비동기 프레임워크가 필요 없다.
  - 새 의존성이 없어 보드 메모리와 설치 위험을 줄인다.
  - 응답 p95 200ms(SC-003)는 메모리 저장소 조회라 충분하다.
- **Alternatives**: FastAPI + uvicorn은 의존성이 늘고 메모리가 수십 MB 늘어 기각했다. 나중에 필요하면 옮길 수 있게 라우터를 분리해 둔다.

## R6. 데이터 끊김과 신선도

- **Decision**
  - 장치 끊김은 과제 1 `report`의 판정을 재사용한다: 마지막 수신이 max(10분, 기대 주기 × 2)보다 오래면 끊김. 사건형 장치(문 센서)는 제외한다.
  - 공간 신선도는 그 공간 대표값의 마지막 관측 칸 나이(분)다.
  - 신선도에 따른 동작

    | 신선도 | 동작 |
    |---|---|
    | 15분 이하 | 정상 |
    | 15~60분 | 예측·상태는 내되 `stale: true`, 이상 판단은 보류 |
    | 60분 초과 | 예측 멈춤(`unavailable: data_gap`) |

    한도는 설정값이다.
  - 근거: 과제 3 입력은 관측 칸 비율 10% 미만이면 예측 불가(min_input_obs)였다. 같은 기준을 쓴다.
- **Rationale**: 끊겨도 서비스는 돌고, 믿을 수 없는 결과는 숨기지 않고 표시한다(헌법 VI).

## R7. 경보 상태 기계와 재발송(생각해 볼 점 Q2)

- **Decision**
  - 경보 키는 (종류, 공간, 장치)다. 상태 전이는 `none → active`(첫 판정) → `active`(재알림) → `cleared`(해제)다.
    - 첫 판정 시 즉시 발행한다.
    - 계속되면 `renotify_min`(기본 30분)마다 다시 발행한다.
    - 해제는 연속 `clear_after`(기본 3) 주기 정상 뒤 `cleared`로 발행한다.
  - 같은 경보를 매분 보내지 않는다.
  - 경보 종류

    | 종류 | 출처 |
    |---|---|
    | `co2_over_forecast` | 예측상 1,000ppm 초과 예상 |
    | `ventilation_soon` | 과제 5 분류기 |
    | `anomaly` | 과제 4 |
    | `data_gap` · `stuck` · `out_of_range` | 규칙 |
    | `model_drift` | 심화 |
    | `service_degraded` | 판단 일부 불가 |
- **Rationale**: 매분 같은 경보는 소음이 되고, 운영자는 알림을 끈다(과제 4 상황). 재알림이 있어야 지속 문제를 잊지 않는다. 해제 지속 조건은 경계값 근처의 깜빡임을 줄인다.

## R8. 모델 묶음 적재와 실행 방식

- **Decision**
  - 시작 시 각 묶음의 `bundle.json`을 읽어 다음을 검사한다.
    - 입력 규약 버전·특징 순서·정규화 통계
    - 데이터 해시 기록 여부
    - 서비스가 지원하는 규약 버전 목록과 일치
  - 실패한 묶음은 그 판단만 끈다.
  - 실행 방식은 과제 7 결과 파일(`var/edgeopt/runtime/runtime.json` 등)에 TensorRT 엔진과 검증(오차 1ppm 이하) 기록이 있으면 TensorRT, 없으면 PyTorch다.
  - GPU가 보이지 않으면 CPU로 실행한다. 실제 방식은 `health`와 각 결과의 `runtime` 필드에 적는다.
  - 묶음 파일이 바뀌면(해시 변화) `infer reload`로 다시 적재한다. 서비스는 재시작하지 않는다.
- **Rationale**: 과제마다 완료 시점이 다르다. 판단 단위로 켜고 꺼야 서비스를 먼저 운영할 수 있다.

## R9. 기록과 12시간 요약

- **Decision**
  - 주기 기록·경보 이력·장애 시험 기록은 **MySQL 팀 DB의 새 표**(`svc_cycle`, `svc_alert`, `svc_forecast_log`)에 쓴다.
  - DB가 끊기면 과제 1과 같은 방식으로 로컬 SQLite 스풀(`var/service/spool.db`)에 쌓았다가 넣는다.
  - `infer report --from --to`가 다음 요약을 Markdown으로 낸다.
    - 예정·완료·실패·건너뜀 주기 수
    - 단계별 처리 시간 p50·p95·최대
    - 경보 내역(종류별 건수·대표 사례)
    - 장애 시험 결과
    - 메모리·GPU 사용 추이(tegrastats 표본)
- **Rationale**: 다른 팀·LLM 에이전트도 SQL로 이력을 볼 수 있다. 과제 1에서 검증한 무손실 스풀을 재사용한다.
- **Alternatives**: 파일 로그만 남기면 요약·조회가 번거로워 기각했다.

## R10. LLM 에이전트가 도구로 쓰려면(생각해 볼 점 Q3)

결과에 다음을 넣는다.
- 단위(`unit`), 기준 시각과 신선도(`t0`, `freshness_min`)
- 불확실성: 예측 구간. 과제 6 사전학습 모델 구간 또는 과제 3 잔차 분위수
- 근거: 이상 원인 상위 3과 기여도, 경보의 근거 값
- 권장 행동 문장과 알림 대상
- 모델 버전·해시와 실행 방식
- `/v1/openapi.json` 스키마
- 짧은 자연어 요약 필드 `summary_ko`. 예: "회의실 CO₂ 23분 뒤 1,000ppm 초과 예상(현재 812ppm)"

에이전트가 숫자를 잘못 해석하지 않도록 필드 이름에 단위를 붙이지 않고 `unit`을 따로 둔다. 각 응답은 스스로 설명적이게 한다.

## R11. 심화 1 — 제어 규칙 시뮬레이션

- **Decision**
  - 규칙: "환기 선제 경보 또는 예측상 30분 안 1,000ppm 초과 → 환기 시작, 예측이 800ppm 아래로 30분 유지되면 종료"
  - 효과 모형: 환기 중 CO₂가 1차 감쇠로 외기 수준(약 450ppm)으로 접근한다.
    - 감쇠 속도는 과제 2 진단의 퇴실 뒤 감쇠(실습실 18시 이후)에서 추정한 시간 상수를 쓴다.
    - 환기 시 시간 상수는 그 값의 1/k(가정 k=2, 3 민감도)다.
  - 지난 7일 실데이터에 서비스 경로의 예측을 다시 돌린다(재생). 규칙이 켜진 구간부터 모형으로 CO₂ 궤적을 고쳐 쓴 뒤 1,000ppm 초과 시간을 비교한다.
  - 가정·민감도를 표로 낸다.
- **Rationale**: 실제 제어를 하지 않고(권한·안전) 데이터로 효과 상한을 추정한다. 가정을 명시해 과장하지 않는다.

## R12. 심화 2 — 자기 성능 감시

- **Decision**
  - 주기마다 예측(지평 5·15·30·60분)을 `svc_forecast_log`에 저장한다. 정답 칸이 닫히면 채점한다.
  - 24시간 이동 MAE가 과제 3 시험 MAE(묶음의 요약값)의 2배를 넘으면 `model_drift` 경보를 낸다.
  - 사용 시간대만 따로 본다.
  - `GET /v1/health`에 이동 MAE를 넣는다.
- **Rationale**: 계절·배치 변화로 모델이 낡으면 스스로 알린다. 과제 3에서 학습(가을·겨울)과 시험(초여름)의 분포 이동을 확인했다.

## R13. 메모리·GPU

- **Decision**
  - 목표는 서비스 프로세스 1GB 이하다. 모델은 작다(과제 3 약 7만 파라미터, 과제 4 공간당 수만).
  - 비용 구성

    | 항목 | 크기 |
    |---|---|
    | CUDA 컨텍스트 | 약 0.6GB(과제 3 측정) |
    | 메모리 창(5시간 × 장치 25 × 항목) | 수 MB |
  - GPU 사용이 1GB 목표를 넘기면 CPU 추론을 기본으로 한다. 배치 1 지연은 과제 7에서 측정한다.
  - 사용자 서비스 관리자에 GPU 그룹이 반영되려면 재부팅 등으로 관리자가 다시 시작돼야 한다(2026-10-21 그룹 추가). 그 전에는 CPU로 동작한다.
- **Rationale**: 보드는 수집기, 다른 계정 작업(t2 약 1GB), 향후 로컬 LLM과 메모리를 나눠 쓴다.

## 결정 기록 (2026-10-21 사용자)

- **MQTT 발행(R4)**: **B안 — 보드 로컬 브로커**에 발행한다(사용자가 처음 A안을 골랐다가 같은 날 B안으로 바꿈). 공용 MQTT 서버에는 쓰지 않으므로 권한 확인 발행도 하지 않는다.
  - 브로커: amqtt(시험용으로 이미 설치됨)를 systemd 사용자 서비스 `wonil-broker`로 상시 실행한다. `0.0.0.0:11883`에서 받는다(흔한 1883·1884를 피함, 2026-10-21 비어 있음 확인). 재부팅 자동 시작·Restart=always는 수집기와 같다.
  - 권한: 구독은 익명 허용(읽기 전용), 발행은 서비스 계정만(비밀번호는 `.env`에 추가, 출력 금지). 토픽 ACL로 `team2/inference/v1/#` 외 발행을 막는다.
  - 다른 팀은 보드 주소 + 11883으로 구독한다. 결과 형식 문서에 접속 방법을 적는다(공개 저장소이므로 실제 IP는 쓰지 않고 "팀 Jetson 주소"로 적는다).
  - 브로커가 죽어도 서비스는 계속 계산하고 API는 응답한다. 발행은 재접속 뒤 최신값을 다시 retained로 보낸다.
- **조회 API 포트**: 18080. 보드를 다른 계정(t2)과 함께 쓰므로 흔한 8080을 피한다. 설정으로 바꿀 수 있고, 시작할 때 포트가 이미 쓰이면 기록·알림 뒤 종료한다(조용한 실패 금지). 정한 포트는 결과 형식 문서에 적는다.
- **배포 위치**: 별도 서버가 아니라 이 보드(systemd 사용자 서비스 `wonil-inference`)다. 다른 팀은 보드 주소로 접속한다.
