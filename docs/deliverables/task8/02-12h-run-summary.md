- **빠진 데이터와 복구**

  - 냉난방(xflow) 20분치는 InfluxDB에 없어 복구할 수 없다.
  - 서비스는 정지 중 실시간 판단을 이미 냈으므로, 복구는 과거 기록·재학습용이다.

#### 발견한 오경보: 꺼진 냉난방 실내기를 "끊김"으로 판정

- **현상**: 사무실 냉난방 실내기(xflow)에 00:53부터 끊김 경보가 났다. 08:00에는 "마지막 수신 256분 전"까지 올라갔다.
- **사실**: 이 장치는 끊기지 않았다. MySQL에 `power`가 매분 들어왔다(15:43~23:47 UTC 591건, 3분 넘는 빈틈 0).
- **원인**
  - 꺼진 실내기는 `power`만 매분 보내고, 온도·설정 온도는 켤 때만 보낸다(과제 1에서 집중회의실 실내기로 이미 확인한 성질).
  - 서비스는 판단에 쓰는 온도·CO₂·습도만 읽는다. 그래서 이 장치의 마지막 수신을 "마지막 온도"로 보았다.
  - 과제 1 설정에는 집중회의실 실내기만 `periodic_items: [power]`로 적혀 있었다. 사무실·회의실 실내기가 빠져 있었다.
- **수정**(2026-10-22 08:54 적용)
  - 설정 `config/collector.yaml`: 사무실·회의실 실내기에 `periodic_items: [power]`를 추가했다(24시간 실측: `power` 1,42x건, 온도 0~3건).
  - 판정 `src/service/rules.py`: 서비스가 읽는 항목을 주기적으로 보내지 않는 장치는 끊김을 판정하지 않는다. 그런 장치의 끊김은 과제 1 수집 보고(`collector report`)가 `power`로 본다.
  - 시험 `tests/service/test_cycle.py::test_data_gap_skips_power_only_device`를 추가했다.
  - 재시작 뒤 활성 경보가 3주기 만에 `cleared`가 됐다(08:57). 지금 활성 경보는 0건이다.
- **교훈**: 장애 시험은 "센서가 끊길 때 경보가 나는가"만 확인했다. "끊기지 않았는데 경보가 나는가"는 실제 밤 운영에서 처음 드러났다. 12시간 기록이 필요한 이유다.

## 12시간 뒤: 실행 방식을 ONNX Runtime CPU로 교체 (과제 7 결정 적용)

기록이 끝난 뒤 2026-10-22 08:54에 서비스를 다시 시작했다. 실행 방식 교체와 위 오경보 수정을 함께 넣었다.

| 항목 | 12시간(PyTorch GPU) | 교체 뒤(ONNX Runtime CPU) |
|---|---|---|
| 예측 모델 실행 | `torch-cuda` | `onnxruntime-cpu`(이상·상태 모델은 PyTorch CPU) |
| 프로세스 RSS | 1,409MB | **689 → 692MB**(−717MB. 첫 25분. 12시간 평탄 여부는 계속 관찰) |
| GPU 사용 | CUDA 문맥 상주 | 쓰지 않음(로컬 LLM에 비움) |
| 주기 전체 p50 / p95 / 최대 | 767 / 835 / 1,058ms(01:00 이후, 서비스만) | **772 / 892 / 939ms**(09:05~09:20, 16주기 모두 ok) |
| 예측 결과 차이 | 기준 | 같은 입력 3,000건에서 CO₂ 최대 0.0005ppm, 온도 0.00001℃ |
| 예측 3공간 1회 | 11.9ms(PyTorch CPU 기준) | 0.67ms |

- 고른 방식: 과제 7의 `var/edgeopt/runtime/runtime.json`(`runner: ort_cpu`)을 읽는다.
  - ONNX 파일 해시와 "어느 가중치에서 만들었는가"(`source_weights_sha256`)를 지금 묶음과 맞춰 본다. 다르면 PyTorch로 돈다(시험 `test_ort_selection_falls_back`).
  - 장치를 `auto`로 두면 CPU를 고른다. CUDA 문맥을 만들지 않으므로 메모리가 준다.
- 주기 시간은 거의 그대로다. 예측 모델 실행은 원래도 주기의 작은 부분(수 ms)이었다. 추론 단계(약 0.45초)의 나머지는 입력 구성과 이상·상태 판단이다.
