# 과제 7 산출물 ① 최적화 보고서

> **측정 조건**
> - 보드: Jetson Orin Nano Super(CC 8.7), L4T R39, **전력 모드 25W, 클럭 고정 안 함**(sudo 없음 — `jetson_clocks` 불가)
> - 소프트웨어: PyTorch 2.14.1+cu130, ONNX Runtime 1.31.0, **TensorRT 10.16.2(JetPack 시스템 판)**
> - 지연: 호스트 입력 → 실행 → 동기화 → 호스트 출력. **워밍업 50회, 반복 1,000회(3구간)**, 조합마다 새 프로세스. CPU 스레드 6(보드 전체)·1(공존 가정)
> - 결과 차이: 과제 3 시험 표본 전체(40,116개), 기준 PyTorch CPU FP32, 원 단위(ppm·℃)로 비교
> - 같은 보드에서 상시 추론 서비스(과제 8)·수집기·다른 계정(t2) 서비스가 함께 돌았다. 경합 표시는 159개 측정 중 2개
> - 측정 시각 2026-10-21 21:50 ~ 23:20 KST. 숫자 원본: [결과 표](tables/01-runners.md), 다시 만들기 `edgeopt report`

## 결론

> **서비스 실행 방식은 ONNX Runtime CPU(스레드 1)로 정한다.**
> - 결과가 PyTorch와 같다(CO₂ 최대 0.0005ppm).
> - 가장 빠르다(예측 배치 1 기준 0.21ms, 네 모델 한 주기 0.81ms).
> - 추가 메모리가 가장 적다(+38MB).
> - GPU를 전혀 쓰지 않아 로컬 LLM에 GPU를 비워 줄 수 있다.
>
> **TensorRT FP16은 GRU·LSTM에서 확인 기준(CO₂ 1ppm)을 넘는다(최대 2.2~3.0ppm).** TCN과 오토인코더는 통과한다.
> TensorRT FP32(TF32 끔)는 모든 모델에서 기준을 통과하지만, 이 크기의 모델에서는 ONNX Runtime CPU보다 약 6배 느리다(1.27 vs 0.21ms).

| 상태 분류기(과제 5) | — | — | — | — | 그래디언트 부스팅(트리) — GPU 변환 대상 아님, CPU 그대로 |

**실행 경로가 안 된 것과 이유**
- **pip TensorRT 11.4**: 이 보드(sm87)용 빌더 자원이 없고, API도 바뀌었다(`BuilderFlag.FP16` 없음).
  - 그래서 JetPack에 들어 있는 시스템 TensorRT 10.16을 `.venv`에 연결해 썼다(`site-packages/system_tensorrt.pth`).
- **ONNX Runtime CUDA**: `no kernel image is available for execution on the device`. 배포된 휠에 sm87 커널이 없다.
- **ONNX Runtime TensorRT 실행기**: 휠에 들어 있지 않다.
- 위 두 경로는 표에 "실패"로 남겼다.

## 2. 결과 차이 — 원 단위 (해결할 것 3, 확인 기준 1)

| 모델 | PyTorch GPU | ONNX Runtime CPU | TensorRT FP16 | TensorRT FP32 | 판정(기준 1ppm / 0.1%) |
|---|---|---|---|---|---|
| 예측 최종(GRU) | 0.0041ppm | 0.0005 | **2.43**(평균 0.027, p99 0.29) | 0.0004 | FP16 ❌, 나머지 ✅ |
| 예측 GRU(B1) | 0.0041 | 0.0005 | **2.96** | 0.0006 | FP16 ❌ |
| 예측 LSTM | 0.0081 | 0.0003 | **2.21** | 0.0004 | FP16 ❌ |
| 예측 TCN | 0.0004 | 0.0004 | 0.38 | 0.0004 | ✅ |
| 오토인코더(경보 바뀐 비율) | 0% | 0% | 0.006~0.012% | 0% | ✅ |

- **FP16 차이는 드물게 크다.** 평균은 0.03ppm이고 99%는 0.3ppm 안이다. 최대 2~3ppm은 소수 표본에서만 난다. 그래도 기준이 "최대"이므로 불합격이다.
- **원인은 순환 구조다.** GRU·LSTM은 24칸을 차례로 계산하며 숨은 상태를 넘긴다. FP16 반올림 오차가 칸마다 쌓인다. TCN은 쌓이지 않아 0.38ppm에 그쳤다.
- **마지막 층만 FP32로 두는 처방**(계획 research R4)은 효과가 없었다(2.43 → 2.80ppm). 오차가 출력층이 아니라 순환층에서 생기기 때문이다.
- 정확도 영향은 사실상 없다. 시험 CO₂ MAE가 36.274 → 36.272ppm으로 거의 같다. 기준을 지키려면 FP32 엔진이나 ONNX Runtime을 쓴다.

## 3. 지연 — 평균과 느린 쪽 5% (해결할 것 2)

예측 최종(GRU) · 배치 1과 4. CPU는 스레드 6 기준이다.

| 실행 방식 | 배치 1 평균 | 배치 1 p95 | 배치 4 평균 | 배치 4 p95 | 결과 차이 |
|---|---|---|---|---|---|
| PyTorch CPU | 10.6ms | 13.8 | 13.5 | **39.1** | 기준 |
| PyTorch GPU(현재 서비스) | 1.32 | 1.48 | 1.37 | 1.44 | 0.004ppm |
| **ONNX Runtime CPU** | **0.21** | **0.23** | **0.51** | **0.55** | 0.0005ppm |
| TensorRT FP16 | 1.14 | 1.22 | 1.13 | 1.25 | 2.4ppm ❌ |
| TensorRT FP32 | 1.27 | 1.38 | 1.31 | 1.60 | 0.0004ppm |

**다른 모델(배치 1 평균, ms)**

| 모델 | PyTorch CPU | PyTorch GPU | ONNX Runtime CPU | TensorRT FP16 | TensorRT FP32 |
|---|---|---|---|---|---|
| LSTM | 24.5 | 1.44 | 0.30 | 1.13 | 1.34 |
| TCN | 10.7 | 3.36 | 0.30 | **0.63** | 0.70 |
| 오토인코더(실습실) | 1.50 | 1.17 | **0.07** | 0.36 | 0.42 |

**해석**
- **이 모델들은 너무 작아서 GPU가 이득이 아니다.** 파라미터가 7만 개이고, 계산은 수 마이크로초면 끝난다.
  - GPU 경로는 입력 복사 → 커널 실행 → 동기화 → 출력 복사의 고정 비용이 약 1ms다. 그래서 TensorRT도 1ms 아래로 못 내려간다.
  - ONNX Runtime CPU는 복사도 커널 실행 대기도 없어 0.2ms다.
- **PyTorch CPU가 느린 것은 계산이 아니라 파이썬·연산자 호출 비용이다.** 같은 CPU에서 ONNX Runtime은 50배 빠르다. "CPU로도 1ms"라는 README 가정은 ONNX Runtime에서만 맞다.
- 배치 1 → 4는 GPU 경로에서 시간이 거의 같다(고정 비용이 지배). 공간이 늘어도 한 번에 묶어 보내면 비용이 늘지 않는다.

## 4. 메모리·전력 (해결할 것 4)

**네 모델(예측 + 오토인코더 3) 동시 적재, 한 프로세스**

| 실행 방식 | 프로세스 RSS | 모델 적재로 늘어난 몫 | 한 주기(4모델) 평균 | p95 |
|---|---|---|---|---|
| PyTorch CPU | 531MB | — | 14.2ms | 24.6 |
| PyTorch GPU | 1,129MB | +614MB(CUDA 문맥) | 7.1 | 6.2 |
| **ONNX Runtime CPU** | **552MB** | **+38MB** | **0.81** | **0.85** |
| TensorRT FP32 | 1,024MB | +510MB | 3.5 | 3.1 |

- GPU를 쓰는 순간 CUDA 문맥으로 약 0.5~0.6GB가 든다(CPU·GPU 공유 메모리). TensorRT 엔진 자체는 0.1~0.2MB다.
- 지금 서비스 프로세스(PyTorch GPU)는 RSS 1.41GB다. ONNX Runtime CPU로 바꾸면 **약 0.6GB를 아낀다**고 예상했다. 실제 적용(10-22 08:54) 뒤 서비스 RSS는 **689MB**로 720MB 줄었다(CUDA 문맥을 만들지 않으므로 예상보다 조금 더 줄었다).

**전력**(tegrastats 1초 간격, 보드 입력 전력 VDD_IN 기준)
- 대기 전력이 5.7~7.0W로 흔들렸다. 다른 계정 서비스와 우리 서비스가 매분 계산하기 때문이다.
- 측정 중 증가분 중앙값은 다음과 같다. ONNX Runtime CPU는 실행이 짧아(1,000회 0.2초) 표본이 0개였다.

  | 실행 방식 | 증가분 중앙값 |
  |---|---|
  | PyTorch CPU | +1.8W |
  | PyTorch GPU | +0.9W |
  | TensorRT FP16 | +0.8W |
  | TensorRT FP32 | +1.0W |

- **한계**: 1회 0.2~1ms짜리 실행은 1초 간격 전력계로 1회당 에너지를 잴 수 없다. 표의 값은 "연속 실행 중 보드 전력"으로만 본다.
- 결론은 메모리·지연과 같다. 매분 1회 실행이므로 어느 방식이든 평균 전력 기여는 무시할 수준이다. 차이는 상주 메모리(CUDA 문맥)와 GPU 점유에서 난다.

## 5. 결정과 적용

| 항목 | 결정 |
|---|---|
| 서비스 실행 방식 | **ONNX Runtime CPU, 스레드 1**(`edgeopt runtime --runner ort_cpu` → `var/edgeopt/runtime/runtime.json`) |
