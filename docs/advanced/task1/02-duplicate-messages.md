# 과제 1 심화(B) ② 같은 메시지가 두 번 오는 경우(재전송) 찾아 처리하기

> **측정 조건**
> - 실 브로커의 실데이터: 수집기 운영 2026-10-20 16:32 ~ 10-21 13:23 KST(약 20.9시간). 통계는 MySQL `ingest_stats`(분 단위)와 `measurement`
> - 실제 이중 발행 표본: 2026-10-20 실 브로커에서 받은 3분 표본(`tests/fixtures/messages.jsonl`)
> - 수집기 `wonil-collector`(systemd 사용자 서비스), Jetson 전력 모드 기본값(결과에 영향 없음)
> - 코드: `src/collector/dedup.py`, `src/collector/service.py`. 설계 근거: [research R8](../../../specs/001-data-collection/research.md)

## 요약

- **실제로 같은 업링크가 두 번 온다.** ChirpStack이 같은 프레임(같은 `fCnt`)을 메시지 두 개로 발행했다. 운영 20.9시간 동안 메시지 21,681건 중 **688건(3.2%)**이 이런 두 번째 사본이었다.
- **DB 유일키로는 막을 수 없다.** 두 사본은 메시지 ID(`deduplicationId`)가 다르고, 기준 시각(`nsTime`)도 1ms 다르다. 시각이 들어간 유일키로는 서로 다른 행으로 보인다.
- **처리 방법**: 수집기가 최근 2시간 동안 받은 (장치, `fCnt`)를 기억하고, 이미 본 프레임이면 저장하지 않고 `duplicate`로 셈만 한다.
- **결과**: 실시간 수집분 LoRa 42,868행에서 같은 (장치, 항목, `fCnt`)가 두 번 저장된 경우가 **0건**이다.
  재처리로 생길 수 있는 중복(스풀 재기록, 과거 데이터 재적재)은 DB 유일키 `(device_id, item, ts)`가 막는다. 이 유일키의 중복도 0건이다.

## 1. 어떤 "두 번"이 오는가: 실측 사례

2026-10-20 15:42 KST, 실습실 CO₂ 센서 `24e124126d152862`의 프레임 `fCnt 104222`가 **9ms 간격으로 두 번** 도착했다.

| | 수신(보드) | `deduplicationId` | 원천 시각 `time` | 받은 게이트웨이(신호 세기 RSSI) |
|---|---|---|---|---|
| 사본 1 | 15:42:06.593 | `ac86a79e…` | 06:42:06.362Z | `…79304`(−110dBm) |
| 사본 2 | 15:42:06.602 | `6c8449a5…` | **06:47:01.771Z** | `…5dccc`(−109dBm), `…79304`(−53dBm) |

바로 다음 프레임 `fCnt 104223`도 같은 모양(9ms 간격, 게이트웨이 조합만 다름)으로 두 번 왔다.

**왜 생기나**
- LoRaWAN에서는 센서 하나의 전파를 여러 게이트웨이가 동시에 받는다. 네트워크 서버(ChirpStack)는 짧은 시간 창 안에 들어온 같은 프레임을 하나로 합쳐 한 번만 발행해야 한다.
- 이 사례에서는 게이트웨이 수신 보고가 두 묶음으로 나뉘어 각각 발행됐다. 사본 2만 시계가 약 5분 빠른 게이트웨이 `…dccc`를 포함한다. 그래서 원천 시각이 5분 어긋난다.
  이 게이트웨이 때문에 과제 1의 기준 시각을 원천 시각이 아니라 `nsTime`으로 정했다.
- 원인은 브로커나 수집기가 아니라 **네트워크 서버 단계**에 있다. 그러므로 수집기 쪽에서 막아야 한다.

**그 밖의 "같은 메시지 두 번" 경로**

| 경로 | 언제 | 같은 시각(`ts`)인가 | 막는 곳 |
|---|---|---|---|
| ① 네트워크 서버 이중 발행(위 사례) | 상시, 메시지의 약 3% | **아니다**(1ms 차이) | 수집기 프레임 기억(2절) |
| ② MQTT QoS 1 재전달 | 브로커 재접속 직후 | 같다 | DB 유일키(3절) |
| ③ 스풀 재기록 | 수집기가 DB 기록 도중 죽은 뒤 재시작 | 같다 | DB 유일키 |
| ④ 과거 데이터 재적재 | `collector backfill`을 같은 기간에 다시 실행 | 같다 | DB 유일키 |

## 2. 처리 방법: (장치, fCnt)를 2시간 동안 기억

```text
메시지 수신 → 해석(장치 id, fCnt 추출)
           → (장치, fCnt)를 최근 2시간 안에 본 적 있나?
                 예  → 저장하지 않음, ingest_stats.duplicate + 1
                 아니오 → 기억하고 스풀 → MySQL 저장
```

| 설계 결정 | 이유 |
|---|---|
| 키로 `deduplicationId`가 아니라 **(장치, `fCnt`)**를 쓴다 | 이중 발행 사본은 `deduplicationId`가 서로 다르다. `fCnt`는 센서가 전송마다 1씩 올리는 프레임 번호라 같은 전파면 같다 |
| 기억 기간 **2시간**(`window_s=7200`) | 이중 발행은 수 ms ~ 수 초 안에 온다. 반대로 `fCnt`는 장치가 망에 다시 가입(재부팅·배터리 교체)하면 0부터 다시 센다. 영구히 기억하면 재가입 뒤의 새 프레임을 중복으로 버린다. 2시간은 두 경우를 모두 넉넉히 가른다 |
| 메모리에만 둔다(`OrderedDict`, 오래된 것부터 삭제) | 장치 22대 × 2시간 × 분당 1~2프레임 ≈ 수천 개라 메모리 걱정이 없다. DB 조회가 없어 수신 처리가 느려지지 않는다 |
| `fCnt`가 없는 원천(xflow 냉난방)은 검사하지 않는다 | 프레임 번호가 없다. 대신 DB 유일키가 같은 시각 재전송을 막는다 |
| 버린 건수는 분 단위로 DB에 남긴다(`ingest_stats.duplicate`) | "얼마나 버렸나"를 나중에 확인하고, 비율이 갑자기 변하면 네트워크 서버 설정 변화를 의심할 수 있다 |

> 한계: 수집기가 재시작하면 기억이 비워진다. 그래서 이중 발행 두 사본(9ms 간격) **사이에** 재시작하면 둘 다 저장될 수 있다. 이 확률은 무시할 수 있는 수준이고, 실측 남은 중복도 0건이다.

## 3. 재처리 중복: DB 유일키

- `measurement`의 유일키는 `(device_id, item, ts)`이다. 기록은 `INSERT … ON DUPLICATE KEY UPDATE id=id`로 한다. 같은 행이 다시 오면 오류 없이 무시되고, 원래 행은 바뀌지 않는다.
- 이 덕분에 스풀을 다시 기록해도, 과거 데이터를 같은 기간에 다시 적재해도 행이 늘지 않는다. 그래서 "일단 다시 보내기"가 안전하다. 무손실(스풀)과 중복 없음이 함께 성립하는 이유다.

SQL(MySQL 클라이언트 또는 Crowfoot 워크스페이스 "데이터 수집"의 연결)로 확인:

```sql
-- ① 걸러 낸 사본 수와 비율(일별, KST)
SELECT DATE(CONVERT_TZ(minute,'+00:00','+09:00')) AS day,
       SUM(messages) AS messages, SUM(duplicate) AS duplicate,
       ROUND(SUM(duplicate)/SUM(messages)*100, 2) AS pct
FROM ingest_stats GROUP BY day ORDER BY day;

-- ② 남은 중복: 같은 (장치, 항목, fCnt)가 2시간 안에 두 번 이상 저장된 경우 → 0이어야 정상
SELECT COUNT(*) FROM (
  SELECT device_id, item, frame_cnt
  FROM measurement
  WHERE ts >= '2026-10-20 07:33:00' AND frame_cnt IS NOT NULL
  GROUP BY device_id, item, frame_cnt
  HAVING COUNT(*) > 1 AND TIMESTAMPDIFF(SECOND, MIN(ts), MAX(ts)) < 7200
) x;
```

`measurement.ts`는 UTC다. `2026-10-20 07:33:00`은 수집기 운영 시작(16:33 KST)이다.

## 6. 해석

- **"중복 제거"는 어느 단계의 키로 할지가 핵심이다.** 메시지 ID나 시각은 전달 과정에서 새로 붙는 값이라 사본마다 다르다. 반면 센서가 붙인 프레임 번호는 사본끼리 같다. 그래서 **원천(센서)이 정한 번호**로 거른다.
- 프레임 번호는 영원히 유일하지 않다(재가입 시 0부터). 그래서 **시간 창**으로 제한한다. 영구 유일키로 쓰면 오히려 정상 데이터를 버린다.
- 3%를 거르지 않았다면 어떻게 됐을까. LoRa 센서의 행이 3% 넘게 부풀고, 과제 2의 5분 칸 평균에서 그 프레임 값이 두 배 가중된다. 커버율·결측 계산에서도 실제보다 많이 받은 것처럼 보인다.
- 이중 발행 비율은 **네트워크 상태의 지표**로도 쓸 수 있다. 비율이 갑자기 늘면 게이트웨이 추가·이동이나 네트워크 서버 설정 변화를 의심할 수 있다. 과제 8 상시 서비스의 상태 점검 항목으로 넘길 만하다.
