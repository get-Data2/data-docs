# 과제 5 심화(B) ② 회의실 노쇼·예약 없는 사용

> 상태: ⏸ **설계·코드 완료, 실측 보류.** 회의실 실제 예약 기록을 구할 수 없었다(2026-10-21 확인). 회의실 직접 관찰도 아직 없다.

## 규칙(설계)

| 판정 | 조건 | 설정 |
|---|---|---|
| **노쇼** | 예약 시작 뒤 15분 동안 사용 여부 추정이 계속 "비어있음" | `advanced.noshow.after_start_min: 15` |
| **예약 없는 사용** | 예약이 없는 시간에 사용 여부 추정이 15분 이상 계속 "사용중" | `advanced.unbooked.min_minutes: 15` |

- 입력: 실제 예약 CSV(`space_id,start,end`, KST)를 `config/state.yaml`의 `inputs.booking_file`에 지정한다.
- 대조: 결과를 직접 관찰 기록(`state observe meeting …`)과 맞춰 정밀도를 낸다.
- 코드: `src/state/pipeline.py`(`state analyze`), 결과 `var/state/eval/analysis.json`의 `noshow_unbooked`

## 왜 지금 결과가 없나

1. **예약 기록이 없다.** 과제 3에는 CO₂ 급상승에서 거꾸로 만든 "추정 예약"이 있다. 그러나 그것으로 노쇼를 찾는 것은 순환이다.
   - 추정 예약은 "CO₂가 올랐다 = 회의가 있었다"로 만든 것이다.
   - 따라서 추정 예약 시간에는 정의상 사람이 있다. 노쇼가 0건으로 나온다.
   - 마찬가지로 예약 없는 사용도 "급상승이 없었던 사용"만 남는다.
   - 그래서 추정 예약은 쓰지 않았다(`labels.occupancy.meeting_source: none`).
2. **회의실 관찰이 없다.** 관찰 목표(회의 2회 + 빈 시간 2시간)가 0이다.
3. **회의실 사용 여부 추정이 성기다.** 10분 주기 센서 1대라 최근 30분 관측 50% 조건을 자주 못 채운다. 실제 서비스에서 회의실 상태 판단은 시간의 약 3분의 1만 나왔다(과제 8 산출물 ①). 노쇼 판단(15분 안 결정)에는 회의실 입력 창을 60분으로 늘린 재학습이 필요하다.

## 예상과 위험

- **노쇼 15분**은 회의실 센서로는 어렵다. 10분 주기라 15분 안에 관측이 1~2개뿐이다. 회의 직전까지 사람이 있었다면 CO₂ 잔류로 "사용중"이 이어져 노쇼를 놓친다. 산출물 ③의 퇴실 직후 오류(96%)와 같은 문제다.
- **예약 없는 사용**은 상대적으로 쉽다. 회의는 CO₂를 수천 ppm까지 올린다(과제 2: 4,000~7,000ppm). 그래서 예약이 없는 큰 상승은 분명히 보인다.

## 다음 행동

1. 회의실 예약 기록(예약 시스템 내보내기)을 받으면 `booking_file`에 넣고 `state analyze && state report`를 실행한다.
2. 그동안 회의실 관찰을 2회 이상 한다([관찰 안내](../../deliverables/task5/observation-guide.md)).
3. 회의실 입력 창 60분 재학습(과제 5 다음 버전).
