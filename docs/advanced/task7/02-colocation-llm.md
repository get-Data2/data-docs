# 과제 7 심화(B) ② 동시 적재와 로컬 LLM 조합

> **측정 조건**: 네 모델(예측 최종 + 공간별 오토인코더 3)을 한 프로세스에 올리고 한 주기(네 모델 각 1회)를 반복했다(`edgeopt colocate`). 25W, 클럭 고정 안 함.
> 보드 메모리 7,486MB(CPU·GPU 공유). 예약: 운영체제 1.5GB, 수집기 0.2GB.
> LLM 크기는 **가정**이다(1B·3B·7B, 4비트, KV 캐시·런타임 여유 1GB; 2026-10-21 결정). 숫자 원본: [결과 표](tables/02-colocation.md)

## 네 모델 동시 적재

| 실행 방식 | 프로세스 RSS | 모델로 늘어난 몫 | 한 주기 평균 | GPU 사용 |
|---|---|---|---|---|
| PyTorch CPU | 531MB | — | 14.2ms | 없음 |
| PyTorch GPU(현재 서비스) | 1,129MB | +614MB | 7.1ms | CUDA 문맥 |
| **ONNX Runtime CPU** | **552MB** | **+38MB** | **0.81ms** | **없음** |
| TensorRT FP32 | 1,024MB | +510MB | 3.5ms | CUDA 문맥 |

- 모델 자체는 수 MB다. 메모리를 정하는 것은 **GPU를 쓰느냐(CUDA 문맥 약 0.5~0.6GB)**다.
- RSS 500MB대의 바탕은 파이썬 + 넘파이·판다스 + ONNX Runtime 라이브러리다. 서비스 프로세스로 합치면 이미 있는 몫이라 실제로 더해지는 것은 +38MB다.

## 로컬 LLM과 함께 올릴 수 있나

남는 메모리 = 7,486 − 예약 1,740 − 시계열 서비스. 측정 시점에 다른 계정(t2)의 서비스가 **약 470MB**를 쓰고 있었다. 아래 "현실" 열은 이것까지 뺀 값이다.

| LLM(4비트, 가정) | 필요 | ONNX Runtime CPU로 운영 시 여유 | 현실(t2 −470MB) | PyTorch GPU로 운영 시 여유 | 현실 |
|---|---|---|---|---|---|
| 1B | 1,536MB | 3,657MB | 3,187 ✅ | 3,080 | 2,610 ✅ |
| 3B | 2,560MB | 2,633MB | 2,163 ✅ | 2,056 | 1,586 ✅ |
| 7B | 4,608MB | 585MB | **115** ⚠️ | 8 | **−462 ❌** |


## 제안

1. **시계열 모델은 ONNX Runtime CPU(스레드 1)로 돌린다.** GPU를 LLM에 통째로 비워 주고, 메모리를 0.6GB 아낀다.
2. **LLM은 3B(4비트)까지가 안전하다.** 여유가 2GB 넘게 남아 임베딩 모델(수백 MB)도 함께 올릴 수 있다.
3. **7B는 시계열을 CPU로 돌려도 여유가 0.1GB 남짓이다.** 다른 계정 작업이나 긴 문맥(KV 캐시)이 조금만 늘어도 메모리 부족 강제 종료가 난다. 과제 3 학습 중 실제로 겪었다(2026-10-21 17:01). 권하지 않는다.
4. 스왑이 없는 보드다. 서비스마다 systemd `MemoryMax`(추론 1.5GB, 브로커 128MB)를 둬서 한 프로그램의 폭주가 다른 서비스를 죽이지 않게 한다. LLM 서비스에도 같은 상한을 둔다.
