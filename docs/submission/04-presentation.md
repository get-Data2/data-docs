## 3. 핵심 결과 ① 일과가 정해진 실습실은 이겼고, 회의실은 못 넘었다 (50초)

| CO₂ 60분 MAE | 현재값 유지 | GRU(우리) | 개선 |
|---|---|---|---|
| 실습실 | 83.9 | **39.3** | **53% ✅** |
| 사무실 | 73.4 | 52.0 | 29% ❌ |
| 회의실 | 177.8 | 142.6 | 20% ❌ |

(MAE = 60분 뒤 예측과 실제 CO₂의 평균 차이, ppm. 시험 2026-05-27 ~ 07-22. 목표는 현재값 유지보다 30% 이상 작게)

- 가장 큰 몫은 **시간 정보**다(검증 46.7 → 34.0ppm). 일정 정보는 경계 직후 오차를 22% 줄였다.
- 회의실은 오차 상위 20개가 모두 **회의 시작 직후**다. 예약을 알면 −28%(상한)다.

말할 것: 모델이 못 하는 것은 "과거에 없는 정보"다. 회의 예약이 다음에 꼭 필요한 데이터다.

## 4. 핵심 결과 ② 고장은 잡지만, 헛경보는 기준의 4.6배다 (40초)

| 주입 고장 60건 | 결과 |
|---|---|
| 탐지율(모델 + 규칙) | **87% ✅** |
| 헛경보 | 검증 0.47 → 시험 **4.65회/일 ❌** |

| 헛경보 원인 | 근거 |
|---|---|
| 계절(학습 가을·겨울, 시험 초여름) | 7월 전에도 2.8회/일, 원인의 57%가 습도 |
| **실습실 센서 1대 결측(07-06~)** | 그날부터 실습실 0.10 → 3.41회/일 |
| 회의실 실제 사용 | 회의 시작 급변 |

말할 것: 처음엔 "계절 하나"로 설명했는데, 다시 파 보니 7월 급증의 큰 몫은 센서 하나가 꺼진 것이었다. 처방도 둘이다. 장치가 빠져도 버티는 입력 처리, 그리고 여름을 넣은 재학습.

## 5. 가장 의외였던 발견: 학습 안 한 모델이 우리 모델을 이겼다 (70초)

| CO₂ 60분 MAE(ppm) | 실습실 | 사무실 | 회의실 |
|---|---|---|---|
| 우리 GRU(1년치 학습) | **38.4** | 51.6 | 141.4 |
| Chronos-2(**학습 0**, 과거 1주만) | 41.2 | **48.4** | **122.8** |

(GRU 38.4는 씨앗 3개 예측의 평균이다. 3장의 39.3은 씨앗별 오차의 평균이라 조금 다르다.)

- 검증 기간에서도 같았다. 시험을 보고 고른 결과가 아니다.
- **왜?** 과거를 1주 주면, 모델이 지난 7일의 같은 시각에서 **하루·주 주기를 스스로 읽는다.**
  - 우리 GRU가 "시간대·요일" 특징으로 얻던 정보를 긴 과거가 대신한다.
  - 과거 1시간 → 1주로 늘리자 오차가 104 → 42ppm으로 줄었다.
- 일과표대로 움직이지 않는 사무실·회의실에서는 우리가 넣은 고정 일과표가 도움이 되지 않았다(과제 3: 사무실 일정 효과 구별 불가). 과거 1주는 그 공간의 **실제** 주기를 보여 준다.
- 대가는 크기다. 1회 87ms(우리 0.9ms), 메모리 1.9GB다. 로컬 LLM과 함께 상주시킬 수 없다.

말할 것: "범용 모델은 대충 맞는다"고 생각했는데 아니었다. 새 공간이나 계절이 바뀔 때 바로 쓸 예비 예측기로 채택했다.

## 6. 두 번째로 의외였던 것: 작은 모델에는 GPU가 가벼운 CPU 실행보다 느리다 (40초)

| 예측 1회(배치 1) | 지연 | CO₂ 차이 |
|---|---|---|
| PyTorch CPU | 10.6ms | 기준 |
| PyTorch GPU | 1.3ms | 0.004ppm |
| TensorRT FP16 | 1.1ms | **2.4ppm ❌**(순환 계산에서 반올림 누적) |
| **ONNX Runtime CPU** | **0.21ms** | **0.0005ppm** |

(예측 모델 GRU 1회 평균 지연. CO₂ 차이 = PyTorch CPU 결과와의 최대 차이, 기준 1ppm 이하. 25W)

말할 것: 모델이 7만 파라미터라 GPU의 고정 비용(~1ms)을 못 넘는다. 서비스는 CPU 런타임으로 간다. 실제로 바꿨더니 서비스 메모리가 1.41 → 0.69GB가 됐다. GPU와 메모리를 LLM에 비워 준다.

## 7. 운영 상태와 다음 행동 (40초)

- **상시 서비스**
  - 12시간 무중단을 마쳤다. 720/720 주기 정상, 재시작 0, 메모리 평탄이다.
  - 수집기를 10분 멈추면 10분 뒤 끊김 경보가 나고, 다시 켜면 3분 안에 복귀한다.
  - 다른 팀은 조회 API와 MQTT로 쓴다. 결과 형식 문서가 있다.
- 가동하며 실제 문제 두 가지를 찾아 고쳤다.
  - DB 연결이 첫 조회의 스냅샷에 갇혀 새 데이터를 못 봤다. 자동 커밋으로 고쳤다.
  - 밤에 꺼진 냉난방기를 "센서 끊김"으로 7시간 경보했다. 꺼지면 전력값만 보내는 장치였다. 장애 시험으로는 안 보이고 실제 밤 운영에서만 드러났다.
- 12시간 뒤 ONNX Runtime CPU로 바꿨다. 메모리가 1.41 → 0.69GB가 됐다.
